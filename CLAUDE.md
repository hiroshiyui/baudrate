# Baudrate: ActivityPub-enabled Bulletin Board System

Public BBS / Web Forum built with Elixir/Phoenix + LiveView, federating via **ActivityPub**.
Baudrate is a **public information hub**, not a social network — public content
should remain visible to all; blocking controls interaction, not visibility.
**The aim is a boring but friendly environment for online discussion**
([ADR 0056](doc/adr/0056-boring-but-friendly.md)) — read it before adding any
feature whose purpose is the return visit. Nothing here is ranked by
engagement and there is no river of posts across boards
([ADR 0054](doc/adr/0054-attention-follows-the-board-not-a-ranking.md), with
[0055](doc/adr/0055-unanswered-is-a-river-and-tags-is-a-ranking.md) removing
its one exception that crossed boards): a hub helps you find the board you
want, it does not decide what you should look at today.
**Information security is the top priority** — this is a public-facing system.

## Quick Reference

```bash
# Requires: Elixir 1.19 / OTP 28 (see .tool-versions), PostgreSQL 15, libvips, Rust toolchain (Ammonia, scraper, feedparser-rs NIFs)
mix setup              # Install deps, create DB, build assets
mix phx.server         # Start dev server (https://localhost:4001)
mix test --seed 9527   # Run all tests (use seed 9527 for deterministic order)
mix test path/to/test  # Run specific test file
mix test --failed      # Re-run previously failed tests
mix precommit          # Pre-commit checks: compile --warnings-as-errors, unlock unused, format --check-formatted, lint (credo --strict), test

# Run tests in parallel with 4 partitions (preferred for full suite):
for p in 1 2 3 4; do MIX_TEST_PARTITION=$p mix test --partitions 4 --seed 9527 & done; wait
```

### Contexts

- **Auth** (`lib/baudrate/auth.ex`) — authentication (login, registration, TOTP, WebAuthn/FIDO2 security keys, sessions, password reset), account recovery (replaceable recovery codes, OpenPGP recovery contacts, admin-issued reset links — ADR 0058), user management (avatars, invite codes, blocks, mutes), registration defences and IP bans (ADR 0063), the limits on new accounts (ADR 0064)
- **Content** (`lib/baudrate/content.ex`) — boards, articles, comments, likes, boosts, polls, permissions, board moderators, search, link previews, article drafts
- **Federation** (`lib/baudrate/federation.ex`) — AP actors, outbox, followers, announces, delivery, user outbound follows, timeline item replies, timeline item likes/boosts, mentions, actor updates, remote-follow handoff (ADR 0059's sibling in Phase 4E)
- **Messaging** (`lib/baudrate/messaging.ex`) — 1-on-1 direct messages, conversations, DM access control, federation
- **Setup** (`lib/baudrate/setup.ex`) — first-run wizard, RBAC seeding, settings, role level utilities
- **Moderation** (`lib/baudrate/moderation.ex`) — reports (including member reports of timeline items, received DMs and remote accounts), resolve/dismiss, audit log, posts held for review and content filters (ADR 0065)
- **Notification** (`lib/baudrate/notification.ex`) — in-app notifications, unread counts, mark read, cleanup, admin announcements, account security notices
- **Bots** (`lib/baudrate/bots.ex`) — RSS/Atom feed bot accounts: CRUD, feed scheduling, deduplication, favicon fetcher
- **AccountMigration** (`lib/baudrate/account_migration.ex`) — account aliases (`alsoKnownAs`) and moving accounts with ActivityPub `Move` (ADR 0025)
- **Retention** (`lib/baudrate/retention.ex`) — the hourly purges: untouched timeline items, old announces, soft-deleted articles and comments and their image files (ADR 0040)
- **DataPortability** (`lib/baudrate/data_portability.ex`) — self-service data export requests (eligibility, cooling-off, cancellation, download cap) and the archive builder (ADR 0023)

### Key Gotchas

- **Nothing is ranked by engagement, and no page rivers posts across boards** (ADR 0054). No `/popular`, `/trending`, `/hot`, `/recent` or `/top`; the home page lists boards, not the articles inside them; board cards carry no post count; the order is the admin's `Board.position`, never activity. A ranking is not a measurement but a feedback loop — what it surfaces gets read, which keeps it surfaced, so attention settles on whoever already had it and a quiet board never appears — and engagement cannot tell an argument from a conversation, so ranking on activity promotes a flame war to the front page, to everyone. Deliberately **unaffected**, because none of it is the site choosing for a reader: chronological order *within* a board, search, tag pages, the syndication feeds, the personal timeline (ADR 0039), and per-viewer unread markers. **`/unanswered` is refused too** (ADR 0055, amending 0054): it ranks nothing, but a cross-board list of articles is a river whatever orders it, and filtering by reply count is mostly filtering by age — newest-first it is `/recent` with a filter that removes almost nothing, oldest-first it is a scoreboard of neglect. A per-board `/boards/:slug/unanswered` would violate nothing and is simply not built. **`test/baudrate_web/no_content_ranking_test.exs` is the acceptance gate**; it covers the four falsifiable shapes, and whether some *new* surface is a ranking is a judgement review has to make.
- Layout receives `@inner_content` (NOT `@inner_block`) — use `{@inner_content}`
- Do NOT wrap templates with `<Layouts.app>` — causes duplicate flash IDs
- LiveView uses `phx-trigger-action` for session writes (POST to `SessionController`)
- Every authenticated LiveView (mounted under `:require_auth` / `:optional_auth`) MUST end its `handle_info/2` with a catch-all `def handle_info(_msg, socket), do: {:noreply, socket}`. `UnreadDmCountHook` / `UnreadNotificationCountHook` subscribe the user to their DM/notification topics and return `{:cont, socket}`, forwarding `:dm_received` / `:dm_read` / `:notification_created` / `:notification_read` / `:notifications_all_read` into the underlying LiveView. A LiveView with only guarded clauses crashes with `FunctionClauseError` for any logged-in user who receives a DM/notification while on that page.
- Soft-delete uses `deleted_at` timestamps for articles and comments — and `Baudrate.Retention` hard-deletes those rows 90 days later, with their revisions, images and image files (ADR 0040). "Soft" means deferred, not permanent; anything a report references is exempt at any age.
- **Publishing commits with the change** (ADR 0034). A publisher runs inside the transaction that makes the change — a step of its `Ecto.Multi`, or `Federation.federate/2` — and never in `schedule_federation_task/1` or a `Task`: a restart between the commit and the task used to save a post, like, follow or DM and silently drop its activities. `Accept`/`Reject(Follow)` are queued the same way. `Delivery.enqueue/3` calls `pg_notify`, which PostgreSQL delivers only on commit, and `DeliveryWorker` listens on its own connection. `schedule_federation_task/1` is for best-effort work only (remote images, media warming, link previews); `federation_async: false` runs it synchronously in tests and `:discard` drops it. **`test/baudrate/federation/durable_delivery_test.exs` is the acceptance gate.** Inside a caller's transaction, a unique violation or `Repo.rollback` aborts the *whole* transaction: check for a duplicate first, and return an error value for an expected refusal (`AccountMigration.follow_on_behalf/2`).
- **The inbox stores, answers, then processes** (ADR 0034). `Federation.Inbound.accept/4` runs `InboxHandler.admit/2` (the admission checks, in their old order), stores the activity (unique per signing actor and activity id) and the controller answers 202; `InboundWorker` processes it afterwards, 4 at a time and one per remote actor in order, and `InboxHandler.handle/3` re-runs `admit/2` because a domain may have been blocked since. A handler's `{:error, reason}` never reaches the sender — it lands in `inbound_activities.last_error` and the log. Processing is at-least-once, so handlers must stay idempotent under redelivery. `activity_json` is cleared once a row leaves `pending` (it can be a DM); do not keep it longer. In tests `accept/4` processes before returning.
- **A failing server costs one probe, not a slot per job** (ADR 0034). `DeliveryCircuits` opens a domain's circuit after 5 unreachable results (connection errors, timeouts, 5xx, 429) and `DeliveryWorker` leaves its jobs out until a probe succeeds. Classify failures on our side (`:unknown_actor`, `:no_private_key`, an SSRF refusal) as `:neutral`, so a local bug never blames a remote server; any HTTP response other than 5xx/429 proves the server is up. A delivery past its deadline is killed and **recorded** (`Delivery.record_interrupted/2`) — a killed task that left its job untouched was retried on every poll forever.
- **Every object we mint is reachable at a path, never a URI fragment** (ADR 0050). All local AP objects (articles, comments, likes, boosts, polls, DMs) are stamped with a canonical `ap_id` on creation (post-insert, since the URI includes the DB-assigned ID), and every URI is built by `Federation.actor_uri/2` — `:comment` gives `/ap/comments/:id`, `:poll` gives `/ap/polls/:id`. Comments used to be `<actor>#note-N` and polls `<article-uri>#poll`; a fragment never reaches the server, so both dereferenced to the *wrong object* (the Person document, the Article) and no peer could thread, vote or cite. Never mint a fragment id. The rewrite changed a **public identity**, which ActivityPub has no way to announce, so `comments.legacy_ap_id` / `polls.legacy_ap_id` hold what peers already learned: `Content.get_comment_by_ap_id/1` and `get_poll_by_ap_id/1` match **either** column (the one chokepoint all seven `InboxHandler` call sites use), a vote's `inReplyTo` resolves against the article **or** the poll URI, and `publish_comment_deleted/2` emits a second `Delete` under the legacy id — a `Delete` of an unknown object is a no-op, and without it deleting a pre-rewrite comment would leave it standing everywhere. `legacy_ap_id` is matched, never asserted, and never castable. `/ap/comments/:id` and `/ap/polls/:id` carry the owning **article's** `publicly_servable?/1` gate plus three refusals of their own (remote, soft-deleted, non-public). **`test/baudrate/federation/object_identity_test.exs` is the acceptance gate.** Publisher functions use the stored `ap_id` with fallback to `Federation.actor_uri/2`. The inbox handler walks remote reply chains to resolve intermediate replies that aren't stored locally. Every hop is an outbound fetch driven by an attacker-supplied `inReplyTo`, so the walk is bounded four ways: ≤5 hops, ≤3 distinct hosts, a visited-URI set (cycle guard), and two rate limits — `RateLimits.check_reply_chain_fetch/1` keyed on the **target** host (10/min, so many hostile domains cannot combine to amplify against one victim) and `check_reply_chain_domain/1` on the sender (20/min). Deliberately no negative cache; the rate limiter is the bound.
- **A mention addresses, and the board gate still decides** (ADR 0051). `@user@domain` is a *different syntax* from `@name` — `Content.Markdown` has two patterns, because one with a word boundary matched `@alice` inside `@alice@mastodon.social` and linkified it to the **local** `/users/alice`. Remote handles link to `/search?q=…` (which resolves the actor here); never to `https://domain/@user`, a guess at another server's URL scheme. `Federation.Mentions` is the reference half: `warm/2` resolves unknown handles **before the write transaction** (an HTTP call inside one holds a DB connection for somebody else's timeout — ADR 0034) and only populates `remote_actors`; everything downstream uses `known/1`, which only reads, so the object served later is the one that was published. An unresolvable handle stays plain text, silently. **The gate applies at four points, not three** — the `Mention` tag, the `cc`, the delivery job, and the *lookup itself*, which is an outbound request that would otherwise tell a server a member here typed that handle. Bounds: `RateLimits.check_mention_resolve/1` (30/h per user), 8 unknown handles per post, 3 s per lookup, 5 s for the step; `HTTPClient.get/2`'s new `:timeout` can only **shorten** the configured ceiling. Bots never resolve mentions. A blocked domain's actor is never addressed even though its row still exists. **`test/baudrate/federation/mentions_test.exs` is the acceptance gate, plus a case in `publisher_test.exs`'s outbound-gate block — a new mention surface goes in both.** Every caller that asks `Mentions` for anything must preload `:boards`: `article_boards_federated?/1` fails closed, which is how comment mentions were silently dropped.
- **A comment's `inReplyTo` names its parent comment** (ADR 0051). `ObjectBuilder.reply_target_uri/2` is the one definition, shared by the published `Create(Note)`, `/ap/comments/:id` and the replies collection. A remote parent's own `ap_id` is used verbatim, which threads the reply back on the instance it started from; a parent with no usable id falls back to the article.
- **A profile or board change reaches followers, and the test is the rendered document.** `Federation.update_actor/3` wraps the change in `federate/2` (so the `Update` commits with it, ADR 0034) and publishes only when the `Person`/`Group` JSON differs before and after. **Compare documents, never a field list** — a field added to `ActorRenderer` then federates with nothing to remember, and a change the document does not carry (signature, notification preferences, a narrowed `dm_access`) costs no fan-out. The chokepoints are `Auth.Profiles`'s `with_interaction/2` and `Content.Boards.update_board/2`; a new way to change a profile goes through one of them. `Publisher.publish_actor_updated/2` is the one builder — key rotation is the same activity, not a separate one. There is deliberately **no debouncing**: `/profile` saves each section separately, so editing four sends four `Update`s, and coalescing would mean holding an activity in memory, which ADR 0034 forbids. Coalesce in the delivery queue if it ever matters.
- **A closed poll announces its final counts once** (`Content.sweep_closed_polls/0`, hourly from `SessionCleaner`). A poll has no stored "closed" state — `Poll.closed?/1` reads the clock, like a sanction's expiry — so this is the one place that treats closing as an *event*, and `polls.final_update_sent_at` is what makes it happen exactly once rather than hourly or, on a missed run, never. It is stamped even when the board gate refuses the activity: deciding not to announce is a way of having handled it, and stamping only on delivery would retry for ever.
- **Every `baudrate:*` field is declared in `Baudrate.Federation.Context`.** One module owns every JSON-LD `@context` this instance publishes — `object/0`, `activity/0`, `actor/0` — because four modules each held their own copy of the ActivityStreams URI and the extension terms were published **undeclared**, which makes them undefined terms that any consumer expanding the document drops silently. The namespace is the *software's* (`https://github.com/hiroshiyui/baudrate/ns#`), never built from `base_url/0`: two Baudrate instances use the same terms and a per-instance prefix would make them incomparable. Adding a `baudrate:` field means adding a row to that module's table — `test/baudrate_web/protocol_hygiene_test.exs` fails otherwise.
- **NodeInfo counts people and local content.** `users.total` excludes bots and banned accounts; `localPosts`/`localComments` exclude mirrored and soft-deleted rows (it counted every article, so following a busy community reported their output as ours). `activeMonth`/`activeHalfyear` come from `users.last_active_on`, **not** from `user_sessions` — a session lives 14 days and is then purged, so that table cannot answer a question about a month. It is a **date, not a timestamp**, deliberately: the question is which month someone was last here, and a timestamp would record what time of day they read the site for six months. `Auth.Sessions` stamps it on create and refresh, conditionally, so it is at most one write per account per day; it is never cast from params. Both 2.0 and 2.1 are served, and **2.0 must not carry `software.repository`** — its schema has no place for it and a crawler reports the instance as broken.
- **An actor document is cached for 180 s, and only when that is safe.** `no-store` stays the default and stays on every 404 and HTML redirect: the verifier fetches an actor by the request's `keyId`, so a cached wrong answer breaks signature verification for everyone. `public` is used **only while `ap_authorized_fetch` is off** — with it on, the same URL answers 401 unsigned and the document signed, so a shared cache holding it would hand the document to unsigned requesters and defeat the setting.
- **A content warning is a field, never a prefix** (ADR 0052). `summary` and `sensitive` are columns on `articles`, `comments`, `timeline_items` and `timeline_item_replies`; the body is stored as written. Inbound used to be `"[CW: \#{summary}]\n\n" <> body` — a one-way conversion that made the warning indistinguishable from the thing it warned about, so nothing could collapse it, nothing could republish it, and **the reader saw the content anyway**. `Baudrate.Content.ContentWarning` holds the rules for all four schemas: an empty warning is `nil` never `""`, **text implies the flag** (the reverse does not — `sensitive` alone renders the generic warning), bounded at 512. **Outbound `summary` is the warning and nothing else** — it carried a 500-character body excerpt, and Mastodon maps `summary` to `spoiler_text` for every object type, so every article arrived there hidden behind its own opening paragraph. Rows written before v1.31.0 keep their `[CW: …]` prefix and are deliberately not rewritten. The collapse is a `<details>`, not a hook: it must hold when scripting has gone wrong. Its classes (`content-warning*`) avoid every word a cosmetic-filter list targets. **`test/baudrate/federation/content_warning_test.exs` is the acceptance gate.**
- **Video and audio are links, never players** (ADR 0052). They cannot be proxied — that would mean re-serving arbitrarily large files — and embedding them is the hotlink `Media.Proxy` exists to prevent (ADR 0006/0045). `AttachmentExtractor.playable?/1` is the one predicate a renderer branches on; a `timeline_items.attachments` row now holds both kinds, told apart by `media_type`. They used to be dropped, so a post whose point was a video looked empty.
- **A group's Announce is a carrier, and the group speaks only for its own host** (ADR 0053). A Lemmy community is a hub, not a booster: members send activities *to* it and it announces them on, so its `Announce` wraps an **activity** where a Mastodon boost wraps an object. `handle_announce_object/3` accepted only `Note`/`Article`/`Page`, so every post in every followed Lemmy community was silently discarded. The signature on the outer Announce is the *group's* and the inner activity carries none, so the split is by what can be verified: a carried **`Create`** goes to the announced-content path whatever host its actor is on (an object has an origin that can be checked, and that path already binds `attributedTo` to it) and is routed to the boards following the **group**, not the author's; **everything else** (`Update`, `Delete`, `Like`, `Undo`) is honoured only when `Validator.same_host?/2` says its actor is on the group's host — the group's signature proves that host, and that is the entire basis for trusting a relay. An honoured activity then faces every `admit/2` check but `validate_actor_match/2`, and dispatches with **its own** actor. Wrapping is bounded to one level (`Announce` is not a carried type); a relay writes no `announces` row, because a community is not a booster; only embedded activities are carried. **`test/baudrate/federation/group_announce_test.exs` is the acceptance gate** — a new carried type goes in it with its refusals, not just its happy path.
- **One gate decides every inbound interaction** (ADR 0004). Only boards with `min_role_to_view == "guest"` and `ap_enabled == true` are federated. A non-federated board's inbox/outbox/actor endpoints return 404, and Follow activities targeting a non-federated board actor (via the shared inbox) are answered with `Reject(Follow)`. The same gate (`InboxHandler.article_federated?/1`) applies uniformly to **every** inbound interaction with a local article — `Like`, `Announce`, `Create(Note)` replies, and Mastodon-style poll-vote Notes. Applying it to only some of them lets a remote actor guess a slug and inject a comment (plus an author notification) or a poll vote into an article that lives only in a private or AP-disabled board. Refused activities are dropped with `:ok` and a log line, not a 4xx, so remote instances do not retry. **Exceptions** (Like / Announce / reply / vote on local articles in non-federated boards): (a) remote articles (`remote_actor_id` non-nil) — they already exist on the fediverse with their own `ap_id`, so refusing interactions there would break federation semantics; (b) local articles whose author has remote followers — user-actor federation may have already published the article via follower fan-out (e.g. `@user@instance` → `mastodon.social/users/them`), so inbound Like/Announce on the published copy must be honored even if the residing board is not AP-enabled. Local articles whose author has no remote followers and that reside only in non-federated boards continue to reject incoming activities.
- **The same gate applies outbound, and it is `Board.federated?/1` everywhere** (ADR 0043 — read it before touching any of this; it records why a withdrawal is the one thing the gate must *not* stop). Content leaves only for an article that is board-less or in at least one federated board, at five surfaces: `Delivery.enqueue_for_article/4` (the author's own follower fan-out, not just the board fan-out), `Publisher.enqueue_for_followers_and_authors/4` (a user `Announce` names the article URI, whose slug comes from the title), `ObjectBuilder.article_object/1` (`cc`/`audience` carry a board's actor URI and so its slug, and three unauthenticated endpoints serve that object verbatim), `ActivityPubController.publicly_servable?/1` plus the user-outbox count and page, and `Content.search_articles/2` behind `/ap/search` via the opt-in `federated_only: true` — opt-in because the site's own search must keep listing content in boards that do not federate. Use `federated?/1`, never `public?/1`: turning `ap_enabled` off does not remove followers a board already has. **A withdrawal is never gated** — `Delete(Tombstone)` and the four `Undo` publishers pass `intent: :withdraw`, which defaults to `:publish` so a new activity is gated unless it says otherwise. The remote author of a *remote* article is never gated either (ADR 0004's exception, outbound). `test/baudrate/federation/publisher_test.exs` ("withdrawals are never gated by the board") is the acceptance gate — add every new outbound path to it, on both sides of the question.
- Announce (boost) routing: when a followed actor boosts Article/Page content, it is routed to boards that follow the booster and creates timeline items for user followers. Loop-safe: `create_remote_article` does NOT trigger outbound `publish_article_created`, so no re-announce storm. Notes are timeline-only (not routed to boards).
- Site actor (instance actor) is discoverable via WebFinger as `acct:site@host` with `preferredUsername: "site"`, resolved before user/board lookups. The `/ap/site` endpoint returns an Organization actor. WebFinger response includes `properties` with `type: "Organization"`.
- Board WebFinger subject must use bare slug (no `!` prefix) matching `preferredUsername` — Mastodon derives WebFinger queries from `preferredUsername` and rejects subject mismatches with 422. The `properties` field with `type: "Group"` disambiguates boards from users (Lemmy convention).
- Server-driven focus: `push_event(socket, "focus", %{id: "…"})` → global `phx:focus` listener in `app.js`. Use it whenever an action removes the control that had focus (destructive row actions, wizard step changes); otherwise keyboard focus falls to `<body>`. PubSub-driven pages announce arrivals via a dedicated `sr-only` `role="status"` node set by the server — never `aria-live` on a whole list/`<tbody>`. Never give a form a dynamic `id` (e.g. derived from a message count): LiveView remounts it and wipes focus and in-progress input.
- Focus management: Add `data-focus-target` to the primary content container in list/browse pages. JS in `app.js` auto-focuses the first interactive element inside it after LiveView navigation — never on the initial load, so it does not race the browser. **`autofocus` and `data-focus-target` do not fight, and a page may carry both:** the handler returns early while any `[autofocus]` sits inside `#main-content`, so on such a page the marker is simply inert for ordinary navigation and the browser's autofocus wins. The one exception is deliberate — a `?page` change bypasses that guard, so focus still lands in the list, which is what makes a paginated page with a search box work. `search_live` and `admin/pending_users_live` each carry both on purpose; do not "fix" them. Prefer not to add the marker to a form page, because there it is inert and therefore misleading, not because it breaks anything. (ADR 0018's Consequences state this as an absolute prohibition, which is stricter than `app.js` has been since the handler was written.) Links get a `focus-visible` inset box-shadow highlight via `app.css`. **Paginated pages share one mechanism:** render `<.pagination>` and mark the list with `data-focus-target` (or pass `scroll_target`); `PaginationScrollHook` (mounted for every LiveView via `use BaudrateWeb, :live_view`) scrolls back to the list on every `?page` change. Never push `scroll-to-top` from a LiveView; `pagination_consistency_test.exs` enforces this.
- CSS grid track blowout: in **arbitrary** grid templates (`grid-cols-[...]`), a bare `1fr` resolves to `minmax(auto, 1fr)` whose minimum is `min-content`. A long unbreakable token (raw URL, long word) in that column forces the track past its container and breaks the page width — symptom only appears with real federated/RSS content, not short dev/test content. Always write `minmax(0,1fr)` in arbitrary tracks, add `min-w-0` to the content column, and `break-words`/`break-all` on user/remote text. (Standard `grid-cols-N` utilities already use `minmax(0,1fr)` and are safe; `flex-1` content columns likewise need `min-w-0`.)
- **Poll votes are anonymous, and the voter row exists anyway** (ADR 0048 — read it before adding any poll surface; it records why `poll_votes` carries a `user_id` and what the promise actually is). `Polls.get_user_poll_votes/2` is the only read path and takes the asker's own id; there is no voter listing, for anyone. Every surface renders the denormalized counters (`voters_count`, `votes_count`), updated transactionally via `Ecto.Multi` with `FOR UPDATE` locking, and the published `Question` gives each option a `replies` Collection with `totalItems` and deliberately **no `items`**. `test/baudrate/content/poll_anonymity_test.exs` is the acceptance gate. Inbound federated votes go through `InboxHandler.handle_poll_vote_for_article/3`, which enforces the same rules as the local `Content.cast_vote/3` path: the poll must not be closed, and the article must pass the federation gate. That helper returns `:not_a_vote` only when the Note genuinely is not a vote (no poll, or no matching option) — a refused vote returns `:ok` so it is dropped rather than falling through to the comment/DM handlers.
- Rate limiting uses **Hammer 7** (ADR 0012 records the failure modes — it fails *open*): the store is `BaudrateWeb.RateLimit` (`use Hammer, backend: :ets`), started in the supervision tree (`application.ex`) — there is NO `config :hammer, backend:` (that was v6). All app rate checks go through the `BaudrateWeb.RateLimiter` behaviour (`check_rate/3`, stubbable via `Sandbox` in tests); the `Hammer` adapter delegates to `BaudrateWeb.RateLimit.hit/3`, whose `{:allow, count}` / `{:deny, retry_after_ms}` return already matches the behaviour contract. Never call `Hammer.check_rate/3` or `Hammer.delete_buckets/1` directly (removed in v7).
- Auth hooks: `:require_admin` (admin only), `:require_admin_or_moderator` (admin + moderator), `:require_admin_totp` (admin re-verification, 10-min sudo mode — accepts TOTP or WebAuthn; skips non-admin users; sudo attempts are capped at 5 / 15 min **per user** via `RateLimits.check_admin_sudo/1`, hit before verification — the cookie counter alone was resettable; WebAuthn assertions must advance the stored sign counter or fail with `:sign_count_regressed`), `:require_auth` (any authenticated user), `:optional_auth` (load user if present), `:require_password_auth` (password-verified session), `:redirect_if_authenticated` (guest-only pages), `:rate_limit_mount` (WebSocket mount rate limit)
- WebAuthn challenges: `WebAuthnChallenges.put/2` stores the full `Wax.Challenge` struct (not a plain map) in ETS — Wax needs `challenge.issued_at` and other fields during `Wax.register/3` and `Wax.authenticate/6`. `pop/3` requires the expected purpose (`:attestation` for registration, `:authentication` for assertions): Wax checks only the client-supplied `clientData.type`, so without it an authentication challenge from `/admin/verify` could register a key. ETS match specs use Erlang atom `:"=<"` (not Elixir `:<=`) for the TTL sweep.
- **Changing an account's second factors requires step-up re-authentication** (ADR 0022). Registering or removing a WebAuthn key, and resetting or enabling TOTP, go through `Auth.verify_reauthentication/5` (password, plus an unused TOTP code when enabled; never a recovery code) behind `RateLimits.check_reauth/1`. On `/profile` a success unlocks key management for 5 minutes in socket assigns, and every handler re-checks that deadline server-side. Failures are recorded in `login_attempts`, so the per-account login throttle survives reloads. Before this, a stolen admin session cookie could register the attacker's own key and use it to pass sudo mode. Every factor change also emits an always-delivered account security notice (`security_key_added`/`_removed`, `totp_enabled`/`_disabled`) from the Auth context functions, never from LiveViews, so no path can skip it. Preferences cannot silence these. Never add a factor-changing action (or any new "confirm your password" form) without this check. A lockout kept in socket assigns or the cookie is resettable by the attacker.
- **TOTP codes are single-use, with a one-period grace window** (ADR 0024). Check a stored secret only through `Auth.verify_totp_code/3`: it accepts the current or previous 30-second period (`match_totp_step/3`) and consumes it with one conditional `UPDATE` on `users.totp_last_used_step`, so a used or older code is refused even under concurrency. Never call `NimbleTOTP.valid?` directly, and never keep the replay marker in the cookie (an attacker replays with their own; the old `:totp_verified_at` guard was never even set). Step-up passes `claim: password_valid` so a wrong password does not burn the code. Failed codes at the login step go through `Auth.record_login_totp_failure/2` (`login_attempts.factor = "totp"`, per-account throttle, `totp_login_failed` notice after 3 an hour); step-up must **not** send that notice, since its generic error would become a password oracle. Tests that authenticate twice within 30 s call `forget_totp_use/1` rather than sleeping.
- `wax_` config: `origin` must match `window.location.origin` exactly (scheme + host + port). Set in `runtime.exs` for production, `dev.exs` for dev, `test.exs` for tests (uses per-partition port). A mismatch causes all WebAuthn operations to fail with a client-side `NotAllowedError`.
- Pagination: use `Baudrate.Pagination` for cross-context paginated queries (`paginate_opts/3` + `paginate_query/3`)
- LIKE sanitization: use `Repo.sanitize_like/1` to escape `%`, `_`, `\` in user input for ILIKE queries
- OTP release paths: Never use `:code.priv_dir/1` in module attributes (`@var`) — it resolves to the build directory at compile time, not the release directory. Use `Application.app_dir(:baudrate, "priv/...")` in a function for runtime resolution.
- Avatar sizes are integers `[120, 48, 36, 24]` — never pass string names like `"medium"` to `Avatar.avatar_url/2`
- HTTP Signature signing: `HTTPSignature.sign/5` and `sign_get/3` must NOT return a `"host"` header — `HTTPClient.build_pinned_opts` manages the `Host` header for DNS-pinned connections. Duplicates cause signature verification failures on remote instances.
- Outbound POSTs to non-AP services (e.g. Web Push) must go through `Federation.HTTPClient.post_raw/3`, not raw `Req.post`. `post_raw/3` reuses the SSRF guard and DNS-pinned transport, closing the DNS-rebinding gap where a hostname could resolve to a public IP at validation time and a private IP at request time.
- **Delivery jobs dedup per activity.** The partial unique index is `(inbox_url, actor_uri, activity_id)` for pending/failed jobs; `DeliveryJob.create_changeset/2` derives `activity_id` from the activity `id` (MD5 of the JSON when absent). Never dedup on inbox and actor alone: that silently dropped every later activity (a boost after a like, a `Move` after an `Update`, everything during a remote outage) while one job was pending or retrying.
- Federation outbound delivery: always call `KeyStore.ensure_user_keypair/1` before enqueuing signed activities (Follow, Undo, etc.) to guarantee the user has an RSA keypair. As a backstop, `Delivery.get_private_key/1` (the signing chokepoint for `send_accept`/`send_reject`/queued `do_deliver`) is self-healing: it lazily generates a keypair for any existing local user/board/site actor that lacks one and never leaks a bare `:error`. This covers new users whose user-signed activity (e.g. a Like on an article in a federated board) is delivered to *board* followers before their own actor was ever fetched — the keypair-generation gap that previously crashed delivery with a `CaseClauseError`.
- **What counts as a "referenced" remote actor comes from the catalog, never from a list in the code.** `StaleActorCleaner.referencing_columns/0` reads every foreign key pointing at `remote_actors` out of `pg_constraint`, because deleting an actor cascades: most of those keys are `ON DELETE CASCADE`, and the rest are `SET NULL`. The check was six hand-written queries against nineteen foreign keys, so an actor that only the other thirteen pointed at looked unreferenced — sweeping an account that had gone quiet for 30 days silently deleted its followers' `user_follows` rows and every `timeline_item` it had posted, and raised `Ecto.ConstraintError` (aborting the whole run) when it reached one with a conversation. Do not "simplify" this back into an explicit list, and do not add a reference-counting column to `remote_actors` that has to be maintained. If the catalog query returns nothing, the run is abandoned rather than treating every actor as unreferenced.
- Actor resolution origin-binding (ADR 0046): `ActorResolver` rejects a fetched actor document whose `id` host differs from the URL it was fetched from (`{:error, :actor_id_origin_mismatch}`). Because signature verification fetches by the request's `keyId` host, this prevents a host from forging an actor on another domain (with its own key) and poisoning the cached `remote_actors` row. Do not relax this to trust `json["id"]` blindly.
- Inbound `Move` authorization (`AccountMigration.handle_inbound_move/2`, ADR 0025): the target actor must claim the moving actor in its `alsoKnownAs` (a local target: `users.also_known_as`) before follows are migrated, and the `Move` `object` must be the signer. The handler force-refreshes the target (`ActorResolver.refresh/1`) and rejects with `{:error, :move_not_authorized}` otherwise — without it, any remote actor could redirect its local followers onto an arbitrary account. `RemoteActor.also_known_as` stores the captured aliases. Each local follower sends `Undo(Follow)` to the old actor and a real **pending** `Follow` to the new one; never repoint the old row as accepted (the removed `migrate_user_follows/2` did, so the new server never knew about the follower and delivered nothing). Board follows are never repointed (admins get `board_actor_moved`), a target with `movedTo` is ignored, and one `Move` per origin is processed every 30 days (`remote_actors.moved_at`, claimed with a conditional `UPDATE`). An authorized Move migrates the follow **and** the timeline items together (`Federation.migrate_timeline_items/2`, repointing both `remote_actor_id` and `boosted_by_actor_id`): timeline membership is a query-time join on `user_follows`, so moving only the follow erases the actor's whole published history from its followers' feeds and makes those items fail `timeline_item_accessible?/2` (no like, boost, reply, or forward). Articles and comments are deliberately **not** repointed — they are board content with their own permalinks and `ap_id`s and stay published under the old actor upstream.
- Announce (boost) authorship origin-binding (ADR 0046): `InboxHandler.handle_announce_object/3` refuses to attribute a boosted object to a cross-origin actor. An object's `attributedTo` host must match the object `id` host (`announce_attribution_bound?/1`); in the fetched path the object `id` host must also match the URL it was fetched from (`same_host?/2`). Without this, a followed booster could route an `Announce` whose embedded/fetched object claims `attributedTo: @victim@other-instance`, materializing attacker-chosen content (and a chosen `ap_id`, poisoning future genuine posts) attributed to the victim. A missing `attributedTo` is allowed — authorship falls back to the booster, the verified Announce signer. Legitimate Mastodon/Lemmy boosts are unaffected (object `id` and author live on the same host).
- **Object and activity origin binding** (ADR 0046 — every one of these is the same rule: a claim about an identity is honoured only from the host that can prove it). `Validator.validate_activity/1` requires the activity `id` host to equal the actor host (`:activity_id_origin_mismatch`), and every `Create`/`Update` path calls `Validator.validate_object_origin/2` so an object `id` must live on the signer's host. `ObjectResolver` (user-triggered import) applies the same rules: the fetched document's `id` host must match the fetch URL and its `attributedTo` host must match the `id`. Without these, any sender could mint objects and activities under another instance's URIs and squat them in the unique `ap_id` columns, so the genuine post is later dropped as a duplicate. `Validator.same_host?/2` is the shared primitive — **the** one, deliberately strict about an empty host; `InboxHandler` delegates to it rather than keeping the private copy it used to have.
- **`Accept`/`Reject(Follow)` are scoped to the signer** (ADR 0046). `Follows.accept_*_follow/2` and `reject_*_follow/2` take the signing remote actor and match `remote_actor_id` as well as the Follow `ap_id`; an embedded Follow whose `object` names another actor is ignored. Follow ap_ids are minted locally and are not secret, so an unscoped lookup let any verified actor flip someone else's follow of a third party.
- **Announce never re-homes content the booster does not own** (ADR 0046). The embedded-object path refuses local URIs (like the fetched path), and `maybe_route_announce_to_boards/3` links an existing article into following boards only when its `remote_actor_id` is the resolved author. Otherwise a followed booster could Announce `<base>/ap/articles/<private-slug>` and have a private-board article listed in public boards.
- **Non-public remote content stays off public surfaces.** Remote comments and articles keep their derived `visibility`, and ingest is deliberately **not** refused, so a peer mis-addressing content loses visibility rather than data. That makes the query filter the only thing between a `followers_only`/`direct` remote row and a public listing, and it is **per query** — there is no chokepoint, because `Filters.apply_article_hidden_filters/3` returns the query untouched for guests and for anyone with empty block lists, so it cannot host the check. `Filters.exclude_remote_nonpublic/1` is the one definition; every listing applies it (or an equivalent join-aware clause): board listings, search (articles **and** comments — `search_articles/2` also backs the unauthenticated `/ap/search`), tag pages, bookmarks, profile boosts, unread badges, and the comment lists behind the AP replies collection. The row-level gates are `ArticleHelpers.user_can_view_article?/2` and `ActivityPubController.publicly_servable?/1`, and they refuse these rows to **everyone including admins** — so the listing filter is unconditional too, with no viewer or role branch. Until v1.21.0 articles had no listing filter at all, so a followers-only remote article was listed with its title and digest, and `/ap/boards/:slug/outbox` re-published it to the fediverse stamped `as#Public`. **`test/baudrate/content/remote_visibility_test.exs` is the acceptance gate — add every new listing query to it.** `Visibility.from_addressing/1` recognizes the compact `as:Public` and `Public` forms and ignores non-string entries.
  - **The personal timeline is the one listing whose rule is not "public only"**, and it had no visibility filter at all. `Federation.Timeline.list_timeline_items/2` joins an accepted follow, so for a `Create` the viewer really is a follower of `remote_actor_id` and `followers_only` is theirs to read — refusing it would hide from followers the posts addressed to them. For an `Announce` the join matched `boosted_by_actor_id`, the **booster**, and says nothing about the author: a hostile instance that Announced a victim's `followers_only` post to a booster local people follow put that post's title, body and attachments into the feed of everyone who was never in its audience. So the clause turns on `activity_type`, and `direct` is refused either way (a DM is Messaging's channel, never a timeline row). Mirror it in `count_timeline_totals/4` — that count has now diverged from its query three times.
- **Blocking a domain hides its content at query time, and never deletes it** (ADR 0030). `Filters.exclude_unservable_remote/1` is the one call a listing makes: it applies both the non-public check and `exclude_hidden_remote/1`, so a new listing has one thing to remember instead of two. Where the row is not the first binding (bookmarks, profile boosts, unread badges, the article side of a comment search, timeline items), the clause is written inline against `Filters.hidden_actor_ids/0` — in blocklist mode a semi-join against `domain_blocks`, in allowlist mode the allowed domains as a parameter (an empty allowlist hides every remote actor). `Federation.Timeline`'s hand-written count SQL mirrors the Ecto query and carries the same clause; a count that disagrees with the page offers a pager page that renders empty. Row-level gates use `DomainBlocks.actor_hidden?/1` (`ArticleHelpers.user_can_view_article?/2` and `ActivityPubController.publicly_servable?/1`) — hiding a domain from listings while its permalink still renders, or while we re-publish it over AP, is not a block. Nothing is stamped on a row, so unblocking restores the content by itself; do not add a denormalized `hidden_at` flag (it drifts silently in both directions). **`test/baudrate/federation/blocked_domain_hiding_test.exs` is the acceptance gate — add every new listing query to it.**
- **A single remote actor can be suspended instance-wide** (ADR 0030, decision 6; `Federation.RemoteActors`) — the lever between telling a reporter to block an account personally and blocking every account on its domain. It is the *same* predicate as a domain block (`Filters.hidden_actor_ids/0` matches a blocked domain **or** `remote_actors.suspended_at`), which is what stops the two diverging as listings are added, and `InboxHandler` refuses a suspended actor's activities next to `validate_domain/1`. Suspension is written only through `RemoteActor.suspension_changeset/2`, never `changeset/2`: an actor refresh rewrites every profile field from what the peer sends, and a moderation decision must not be reachable from there. Staff surfaces (the instance detail page at `/admin/federation/instances/:domain`) deliberately keep showing hidden content — moderators cannot judge what they cannot see.
- **A domain block stops us reaching out, not only listening** (ADR 0030, decision 9). `ActorResolver` and `ObjectResolver` refuse to fetch from a blocked domain (`{:error, :domain_blocked}`), the reply-chain walk refuses to follow an `inReplyTo` into one, and the media proxy refuses its images (redirecting to the placeholder, deliberately **not** negative-cached, so unblocking works at once). Because signature verification resolves the actor behind the `keyId`, the `ActorResolver` refusal is also what stops a blocked domain getting a request from us and gaining a cached `remote_actors` row; `VerifyHTTPSignature` answers that case 202-and-drop rather than 401, so the sender does not retry forever. An already-cached actor is still served (blocking deletes nothing) but is never refreshed. The per-hop check is **opt-in per caller** (`refuse_blocked: true` threaded into `HTTPClient`), because applying it unconditionally in the transport would refuse ordinary link-preview fetches in allowlist mode, where `domain_blocked?/1` is true for every non-allowed domain. So every must-refuse caller has to pass it, and they do: `ActorResolver` on **both** the unsigned fetch and the signed retry (a first-hop check alone was bypassable — answering the unsigned GET with 401/403/404 is the documented way to trigger the retry), `ObjectResolver`, the reply-chain walk, `Media.Cache`, and `InboxHandler.fetch_and_handle_announce_object/3`, which also pre-checks the host because a verified sender chooses that URI freely. `drop_signature_headers/1` strips `signature`, `signature-input`, `digest`, `date` and `authorization` on every redirect hop, so a redirect cannot collect credentials addressed to another host.
- **User-facing changesets are allow-lists** (ADR 0049; the local half of ADR 0046's rule — 0046 stops a remote host minting our URIs, this stops a member minting theirs, and the unique `ap_id` column needs both). `Article.changeset/2` casts only `title/body/slug/user_id/forwardable/visibility`; `ap_id` is stamped post-insert, and `url`/`published_at` are reachable only through `Article.trusted_changeset/2` via `Content.create_article(attrs, boards, trusted: true)` (bots). `Comment.changeset/2` likewise never casts `ap_id`. The LiveViews additionally `Map.take` the form fields and always set `parent_id` from the server-side reply target. Casting these from params let any user pre-squat a remote object's `ap_id` (so the genuine post is dropped as a duplicate and the local one is served in its place), plant an arbitrary "View original" link, backdate a post, or thread a comment under a comment in a board they cannot see.
- **A peer-supplied `published_at` is clamped to now.** `InboxHandler.parse_published/1` refuses a future date (with a `validate_change` backstop in `TimelineItem.changeset/2`, 60 s of slack for clock skew), mirroring `Bots.SyndicationFeedParser.clamp_published_at/1` on the other ingest path. The timeline orders on this column, so `"published": "2099-01-01T00:00:00Z"` pinned an item to the top of every follower's timeline — above local articles and comments, which sort by `inserted_at` in the same merge — and retention could not shorten it, because it ages by `inserted_at` on purpose. `Article.remote_changeset/2` does not cast the field at all.
- **A locked or withdrawn article refuses inbound replies too.** `InboxHandler.handle_create_note_comment/2` drops (with `:ok`, so the sender does not retry) a `Create(Note)` whose target is `locked` or soft-deleted. `Permissions.can_comment_on_article?/2` refuses local members on a locked thread and the lock is published as `baudrate:locked`, but nothing checked it inbound — so a moderator who locked a thread in a federated board kept receiving remote replies, each rendering and notifying the author, from the side most of the traffic comes from. The reply-target resolvers use a bare `Repo.get`, which does not filter `deleted_at`, so this is the check.
- **Remote `url` is https-only.** `InboxHandler.extract_url/1` returns `nil` for anything but `https://` (mirroring `ActorResolver.extract_url/1`), and `Article.remote_changeset`, `Comment.remote_changeset`, and `TimelineItem.changeset` carry a `validate_format` backstop. The value is rendered verbatim as an `href` and HEEx does not scheme-check attributes, so a `javascript:`/`data:` value would be a stored link injection held back only by CSP.
- **User-page and personal-timeline listings are viewer-gated.** `Content.list_recent_*_by_user/3` and `paginate_*_by_user/2` take `viewer:` (user or `nil`) and hide articles/comments/boosts in boards the viewer cannot open (board-less articles stay public, matching `ArticleHelpers.user_can_view_article?/2`); pass `socket.assigns[:current_user]` from every caller. `Federation.Timeline.list_timeline_items/2` applies the same predicate to followed users' local articles (and its count SQL mirrors it). Without these, a guest could read private-board titles, board names and comment digests from `/users/:name`, and following an admin surfaced admin-only board posts in the timeline.
- **Session revocation must go through `Auth.Sessions`** (ADR 0008). Every deletion path (`delete_session_by_token/1`, `delete_all_sessions_for_user/1`, `delete_other_sessions_for_user/2`, eviction, expiry and `purge_expired_sessions/0`) broadcasts `"disconnect"` to `live_socket_id` (`"user_session:<row id>"`, set at login and backfilled by `RefreshSession`) after the rows are deleted. A raw `Repo.delete_all` on `user_sessions` leaves already-open LiveView pages acting on a dead session (bans included). Code that must keep "this" session (password change, sign out everywhere) keeps it by **row id** (`Auth.session_id_by_token/1` at mount), never by token: tokens rotate daily.
- **Account migration is gated, delayed and reversible** (ADR 0025; `Baudrate.AccountMigration`). Outbound: aliases and moves need step-up re-authentication; a move needs the data export eligibility plus no staff/board-moderator role and one move per 30 days, waits 24 h (`account_moves`, banner, `cancel_active_moves/2` next to `cancel_active_exports/2`), and is re-checked at send time by the hourly sweep. A moved account (`users.moved_to`) is **read-only at the context boundary**, now enforced by `Auth.ensure_can_interact/1` along with sanctions and bans (ADR 0029, below). `status` is never set to "moved". A moved account may still **follow** people — a move is a redirect, not a punishment — which is why the follow paths pass `moved: :allow`.
- **Backups never delete before a new one succeeds** (ADR 0028; `Baudrate.Backup.Snapshots`, Ansible `backup` role). A nightly backup is a folder built under `.incomplete-…` and renamed only when its dump passed `pg_restore --list` and its uploads snapshot is written. Retention counts complete backups (`:keep`) and runs only after a success; a run refuses to start when it would leave less than 1 GiB or 10% of the disk free. Uploads are hard-linked to the previous backup's unchanged copies, so files inside a backup are shared between folders: never modify them (restore copies out). Each backup carries `CHECKSUMS.sha256` over the dump and every upload, and `scripts/pull-backups.sh` verifies it — after checking the list itself against the hash in `MANIFEST.json`, because `sha256sum -c` on a truncated list exits 0. **A hard-linked file keeps the checksum the previous backup recorded; never re-hash it.** Re-hashing reads the bytes as they are now and records a checksum that matches them, so a file that rotted on disk would be certified intact by every later backup — carrying the original value forward is what makes the rot surface. Do not switch to age-based deletion, nightly tarballs, or a server-side push credential without a new ADR.
- **Data export is designed against leakage** (ADR 0023; `Baudrate.DataPortability`). Do not weaken these without a new ADR:
  - **Who and when:** self-service needs TOTP enabled for ≥ 7 days (`totp_enabled_at`). Request and download both run step-up re-authentication **inside the context**. A request is downloadable 24 h after it is made, for 48 h, at most 3 times (`claim_download/2` is one conditional `UPDATE … RETURNING`). Password change, TOTP disable, ban and sign out everywhere call `cancel_active_exports/2`.
  - **No archive is ever stored:** `Archive.build/2` runs at download time, holding the instance-wide `pg_try_advisory_xact_lock` slot, into `System.tmp_dir!()` (`0600`), and the controller deletes it after `send_file`.
  - **Content:** `Collector` uses explicit field allow-lists only (never `Map.from_struct` or encoding a schema) and the viewer-gated board predicate. Other people's content appears only as URIs, and DMs only as the user's own messages.
  - **Media paths:** rebuilt from a strict hex filename via `DataPortability.Files`, never taken from `storage_path`, with every component confined below the resolved uploads root (no symlinks).
  - **Downloads:** `ExportController` requires Fetch Metadata (`same-origin` / `navigate` / `document`) plus a 60 s token whose claims are matched against the request id, the user and the session row, made single-use by a nonce `DownloadNonces` binds to the user and takes atomically, and answers the same 404 for every other failure (a per-IP limit of 10 per 15 minutes answers 429 first). nginx must not buffer `/exports/`.
  - **Canary gate:** `test/baudrate/data_portability/archive_test.exs` seeds every secret column with markers and fails if one appears in an archive. **Add any new secret column there.**
- **A block stops interaction in both directions, on this site only** (ADR 0026). `Auth.blocked_with_author?/2` refuses comments, replies, likes and boosts (undo stays allowed), forwards, local and remote follows, and timeline item interactions with `{:error, :blocked}` (forwards `:unauthorized`) at the context boundary; the inbox refuses a blocked actor's `Follow` (`Reject(Follow)`) and drops its `Like`, `Announce` and replies on the blocker's content. Blocking deletes follows both ways (`Undo(Follow)` / `Reject(Follow)` via `Federation.sever_remote_follows/2`); no `Block` activity is ever sent. Any new way to interact needs the same check, like `ensure_not_moved/1`. The refusal flash stays neutral (`blocked_interaction_message/0`) and never says who blocked whom.
- **One gate decides whether an account may act at all** (ADR 0029). `Auth.ensure_can_interact/1` returns `:ok` or `{:error, :banned | :account_suspended | :account_silenced | :account_moved}` in one query, and is called at **every** context function that creates content or an interaction: articles, edits, comments, timeline replies, likes, boosts, forwards, poll votes, follows, DMs, invites, and the parts of a profile other people read (display name, bio, avatar, signature, profile fields). When you add a new way to post or interact, call it there — not in the LiveView. `test/baudrate/auth/sanctions_gate_test.exs` walks the AST of `lib/` and fails if the older, narrower `AccountMigration.ensure_not_moved/1` is called outside the two files allowed to ask about the *followed* account. Hide the control too (`interaction_toggle?/3`, `moved_account?/1`, `can_create_content?/1`), but the context is what enforces it.
  - A sanction is a **row in `sanctions` with an explicit end**, never a `users.status` value: `status` stays `active | pending | banned`, because several checks ask `status != "banned"` and would admit a value they have never heard of. Refusing a pending registration is therefore a ban with a reason, logged as `reject_user`.
  - **Active is decided by the clock** — `lifted_at IS NULL AND (expires_at IS NULL OR expires_at > now())` — never by a sweep. Do not add a background job that applies or lifts sanctions: a missed run would hold someone past their time. `SessionCleaner` only sends the "it has ended" notice, and may miss a run without consequence.
  - Sanctions **stack forward only**: any active row restricts, and the end shown is the furthest away, so issuing can only extend. To shorten one, lift it (`Auth.lift_sanction/4` clears every active row of that kind).
  - Undoing an earlier like or boost, deleting your own content, **reporting abuse** and every account-security action stay open to a silenced member. So does narrowing `dm_access`: a sanction must not stop someone making their account safer.
  - A suspension is refused in `authenticate_by_password/2`, re-checked in `AuthHooks` and `SessionController`, and treated as signed-out by `:optional_auth`. It revokes sessions and cancels exports and moves like a ban, but deliberately leaves invite codes alone.
  - Every refusal reaches the member: an always-delivered notice, the flash (`Helpers.refusal_message/3` — route every `{:error, reason}` catch-all through it), and a page-wide banner. A post that fails with a shrug is worse than the sanction.
  - Authority is the `moderator.sanction_user` permission, checked in `Auth`, plus two absolute rules: nobody sanctions themselves, and nobody sanctions an account whose role level is at or above their own. Without `admin.manage_users` the duration is capped at 30 days, measured server-side.
  - **The permission catalogue is fixed at compile time, and only four of its eleven entries enforce anything** (ADR 0042). Nothing outside `Setup.seed_roles_and_permissions/0` writes `role_permissions` — there is no roles admin UI — so `Setup.has_permission?/2` is a constant function of `Setup.default_permissions/0`, and a "permission check" is an indirect way of asking whether a role is `admin`. There is **no runtime inheritance**: the join is exact on `(role_name, permission_name)`, and a higher role holds a lower one's permission only because the seed map lists it again. The four that are consulted: `admin.manage_roles` (role reassignment — the only one with no role-name alternative, so keep it at the context boundary), `moderator.sanction_user`, `admin.manage_users` (which also lifts the 30-day cap and carries ban/unban), `user.create_content`. `test/baudrate/setup/permissions_are_enforced_test.exs` names the other seven in `@known_unenforced` so an eighth fails the build; it **excludes `lib/baudrate/setup.ex`** (which defines the catalogue) and **strips every heredoc and `@doc` before searching**, because a permission quoted as an example in a moduledoc is not enforcement — two of the seven hid behind exactly that, on top of the tautology the file exclusion had already fixed.
- **Accepting the terms is recorded, versioned, and enforced by the same gate as a sanction** (ADR 0031). `users.terms_accepted_at` and `users.terms_version` are written by `User.accept_terms/1` — validation and recording are one function, because they were two (validate the checkbox, discard the answer) and that *was* the bug. Neither field is castable from params: a member who could set `terms_version` would accept a version that does not exist yet. The published version is `settings.eua_version`, moved only by `Setup.publish_terms_version/0` behind a deliberate checkbox — never derived from a hash of the text, which cannot tell a new clause from a corrected typo and would make every edit prompt the whole instance. The pause is `{:error, :terms_not_accepted}` from `Auth.ensure_can_interact/1`, checked **last** (a member who is also silenced is told about the silence, which is the one they cannot lift alone) and inheriting that gate's exemptions — undo, self-delete, **reporting abuse** and account security stay open, and reading is never affected. **Bot accounts are exempt inside the gate's own query**: a bot cannot sign in to accept, and `Content.create_article/3` puts bot posts through the same gate, so without it publishing terms silently stops every RSS feed. The three documents (`eua`, `rules`, `privacy_policy`) render through `Content.Markdown.to_html/1` and live in `live_session :public_browsable`, never `:public` — `:redirect_if_authenticated` would bounce a member off the document they must accept. **`test/baudrate/auth/terms_gate_test.exs` is the acceptance gate — add every new posting path to it.**
- **Site rules are records, and a report may cite one** (ADR 0032). `Setup.Rule` rows carry `position`, `title`, a markdown `body` and `retired_at`; `/rules` numbers them with stable `#rule-N` anchors and `/admin/rules` edits them. `position` is assigned by `create_rule/1` and swapped by `move_rule/2` inside a transaction, never cast from a form — an admin typing a number is how two rules claim the same place. **A rule is retired, never deleted:** it leaves `/rules` and the report dialog, but every report that cited it still resolves, where a hard delete empties the citation on every past report. `reports.rule_id` is always optional, even for `rule_violation` — reporting abuse stays open to members under sanction (ADR 0029) and behind on the terms (ADR 0031), so making someone find the right rule number first contradicts that. The client value arrives through `SafetyActions.report_details/1`, the one place report fields come from the client. `Setup.get_policy/1` therefore covers only `:terms` and `:privacy`.
- **What happens to a cross-posted article needs rights on every board it is in** (P1-D5). `Permissions.board_moderator_for_all?/2` gates deleting, pinning and locking an article and deleting a comment on it; a moderator of one board can only take the article out of that board (`can_remove_from_board?/3`, enforced in `Content.remove_article_from_board/3`). Authors, admins and global moderators are exempt. Board moderators act through `/moderation` (`ModerationLive`), scoped by `Content.moderated_board_ids/1`, and every action re-checks `Moderation.report_in_boards?/2` — never trust the report id from the client. A removal copies the content into `reports.evidence_body` (P1-D6), purged 90 days after the report closes.
- **Member reports of timeline items, DMs and remote accounts go through `Moderation.report_timeline_item/3`, `report_message/3` and `report_remote_actor/3`**, which check the reporter can see the target (`timeline_item_accessible?/2`; a message must be in the reporter's conversation, sent by the other side, not deleted). A message report copies only that message into `reports.message_body`, set from the stored row and never cast from attributes, so moderators never read the conversation. `has_open_report?/2` matches the target exactly.
- DM authorization is enforced in `Messaging.create_message/3` (the context boundary), not only when a conversation is started — block / `dm_access` changes apply to every subsequent message. Returns `{:error, :not_allowed}`.
- Comment forwarding source-board view gate: `Content.forward_comment_to_board/3` rejects (`{:error, :unauthorized}`) when the acting user cannot view the comment's source board (`Interactions.article_visible_to_user?/2`), checked *before* the `comment.visibility` gate. Local comments default to `visibility: "public"` regardless of board `min_role_to_view`, so the visibility check alone would let a user guess a comment ID in a private board and exfiltrate its body into a public board. `Content.forward_article_to_board/3` carries the same gate at the context boundary (it no longer relies on the LiveView's mount-time `socket.assigns.article` being view-gated).
- Forwarding never resurrects soft-deleted content: `forward_article_to_board/3`, `forward_comment_to_board/3`, and `forward_timeline_item_to_board/3` all return `{:error, :not_found}` when the source record has a non-nil `deleted_at`, and `TimelineLive`'s `submit_reply` refuses deleted timeline items. The LiveView handlers fetch the source by a **client-supplied ID** via a bare `Repo.get/2` (which does not filter `deleted_at`), so the moderation/withdrawal decision must be enforced in the context, not in the query.
- `timeline_items` rows are **global** — timeline membership is a query-time JOIN on `user_follows`, not a per-user column. Every entry point that resolves a timeline item from a client-supplied ID (like, boost, reply, forward-to-board) must call `Federation.timeline_item_accessible?/2`, which requires an `accepted` follow on the item's *source* actor and rejects soft-deleted items. The source actor is `boosted_by_actor_id` for `Announce` and `remote_actor_id` for `Create` — using `remote_actor_id` unconditionally breaks boosts, because for an `Announce` that field holds the original author, whom the local user need not follow. **The same two-actor distinction applies to every filter on the timeline**, and its hand-written count SQL must mirror all of them: the mute/block `ap_id` clause has to test the booster as well as the author (`ra` is joined on `remote_actor_id`, so muting someone you follow hid their posts and left their boosts), the instance-level clause has to include `suspended_at` and not just the domain (the count said otherwise and the pager offered an empty page), and the comment branch needs `is_nil(c.user_id) or …`, because a remote comment has no local author and `NULL not in (…)` is NULL — which dropped every federated reply as soon as the viewer blocked anyone.
- **Baudrate runs on one node** (ADR 0033). The ETS caches, WebAuthn challenges, download nonces, Hammer counters, local uploads and every periodic worker are correct *because* nothing else runs against the database: `DeliveryWorker` selects jobs without row locks, and a cache refresh never leaves the node that wrote. There is no cluster discovery (`DNSCluster` and `DNS_CLUSTER_QUERY` were removed). Do not add them back, or a shared rate-limit store, or cross-node invalidation, without superseding the ADR. Anything security depends on across requests stays in the database, where it already is (the TOTP replay marker, `login_attempts`, sanctions, export download claims): never move it into ETS on the strength of this decision. Release tasks (`bin/baudrate eval`) load the application without starting it, so they are not a second node; keep it that way.
- **The detailed health report stays on the host** (ADR 0035). `Baudrate.Health.report/1` is served only by `BaudrateWeb.HealthDetail`, a separate Bandit listener bound to `127.0.0.1` whose address is hard-coded. Never add it as a route on the public endpoint: nginx proxies every visitor from `127.0.0.1`, so "localhost only" there admits everyone. The report holds counts, ages and statuses — no content, account names or remote domains, and a check that raises reports a fixed reason, never the exception text. A periodic worker calls `Health.Heartbeat.beat/1` **after a completed run** (a crash-looping worker is alive but never beats) and needs an entry in `Health`'s worker list. `test/baudrate/health_test.exs` breaks every check. `LOG_FORMAT=json` (`Baudrate.Logger.JSONFormatter`) writes only allow-listed metadata and must never raise: a formatter that raises gets its handler removed, silently ending all logging.
- **A failing check reaches a person, and a working instance stays silent** (ADR 0044, which amends 0035's "Baudrate does not notify"). `Baudrate.Health.Alerts.run/2` runs hourly from `SessionCleaner` — with its state, so it is the one step outside the uniform step list — and sends an always-delivered `health_alert` to `Setup.admin_user_ids/0` after a failing set has survived **two consecutive polls**, repeating daily until a `health_recovered` follows. Keep both halves: an alert that fires on the first poll turns the two flappable queue checks into notifications nobody reads, and one that never repeats is forgotten. "Have we said this already" is answered by querying the notification rows, never a settings row or a new table, so a restart cannot re-announce a week-old problem; the consecutive counter is the only piece in memory, because losing it delays an alert instead of repeating one. **The alert must not move into the backup task** — that can only report a run that failed, never one that never happened, which is the silent case the whole thing exists for. A new check needs a label in `BaudrateWeb.Helpers.translate_health_check/1` in all three locales or admins read a bare identifier. `test/baudrate/health/alerts_test.exs` is the acceptance gate.
- **Retention deletes permanently, and never what a report points at** (ADR 0040). `Baudrate.Retention` runs hourly from `SessionCleaner`: timeline items older than 90 days with no like, boost or reply; `announces` older than 180 days; and articles and comments whose `deleted_at` is over 90 days old, hard-deleted with their image files unlinked. `reports.timeline_item_id`, `article_id` and `comment_id` are all `nilify_all`, so deleting a report's subject would empty the moderation record instead of refusing — every pass therefore excludes anything a report references, whatever its age. Age timeline items by `inserted_at`, never `published_at`: a peer sets that and a future date would pin a row forever. **`bot_syndication_items` is never purged** — it is the `(bot_id, guid)` ledger that stops a feed bot re-posting, not a timeline item, and deleting a row republishes that entry. A cascade does not remove uploaded files, because the orphan sweeps look for rows without a parent, not files without a row: collect the paths before deleting and unlink after. **Rebuild those paths from `filename` via `Baudrate.DataPortability.Files`, never from `storage_path`** — that column is an absolute path into the release directory current at upload time, which the deploy deletes, so for anything old enough to purge it names nothing and the unlink was a silent no-op (`DataPortability.Files` refuses to trust it for the same reason). A missing file is logged, because swallowing `:enoent` is what hid this. Adding a table to the purges means adding it to `test/baudrate/retention_test.exs`, which is the acceptance gate — and a file test must let the module derive the path, not hand it a fabricated one.
- **Secrets at rest are keyed per class, and every key is rotatable** (ADR 0038). `Baudrate.Crypto.Keyring` owns two classes — `:auth` (TOTP secrets, recovery-code hashes) and `:signing` (actor private keys, the VAPID key) — read from `BAUDRATE_AUTH_KEYS` / `BAUDRATE_SIGNING_KEYS`, each an `id:key` list with the current key first. With nothing configured it derives today's key from `SECRET_KEY_BASE` **and `Baudrate.Crypto.Vault` writes the old format**, so an upgrade is reversible; configuring a key is the deliberate step that ends that. Encrypt and decrypt only through the three named vaults (`TotpVault`, `KeyVault`, `VapidVault`), which bind each value to its row — pass the owner, never a bare id you guessed — and which return `:error`, never raise, so a key problem fails closed instead of taking out a request. Adding a new secret column means adding it to `Baudrate.Crypto.Rekey`'s targets (or rotation silently skips it) and to the data-export canary (ADR 0023). Recovery codes are a one-way HMAC: they carry a `key_id`, verification tries every configured key, and the column is never a filter, because a wrong label must not lock anyone out. **Never remove a key while `Rekey.usage/0` still counts values under it** — the health report's `encryption_keys` check is the last warning before members are locked out of their own accounts. Three things keep that warning trustworthy: `"legacy"` is a **reserved id** (`runtime.exs` refuses it, `Vault.encrypt/3` picks the format from `Keyring.separated?/1` rather than by comparing the id, and `Keyring.fetch/2` searches configured keys first) — a configured key of that name was written and read with two different keys, and both the census and the check reported it as fine; `Vault.key_id/1` requires an id to match the same charset configuration enforces, so a legacy blob whose random IV happens to start `BK1` is not reported as a missing key (and its non-UTF-8 bytes cannot crash the health report's JSON); and `usage/0` counts key-id prefixes in SQL rather than loading every ciphertext, so the check does not outgrow its own 5-second budget.
- **The language a page renders in comes from four places, in this order: the `locale` cookie, `session[:preferred_locales]`, `Accept-Language`, then `"en"`.** `BaudrateWeb.Locale` states the order and owns `known?/1`, the allow-list — nothing else may reach `Gettext.put_locale/1`, so an unknown cookie value is ignored rather than carried around. The cookie is first because it is the only one of these a person said out loud; it is a **named one-year cookie, not a session key**, because the session is dropped at sign-out and a preference that resets itself reads as a bug. Step 2 is a **cache written at login and nowhere else**, and only a session write refreshes it: a LiveView cannot write the session, so `/profile` posts its change to `BaudrateWeb.LocaleController` (`save_locales/2` → the hidden `locale-sync-form`, and only when the *effective* locale moved). Before that, changing language left the database and the session disagreeing, so every later full page load rendered its dead HTML — and `lang=` on `<html>` — in the language the member had just left, telling a screen reader the wrong thing every time. The footer switcher is a **`<details>` dropdown holding a plain form POST, on purpose**: `<details>` opens with no JavaScript and no `aria-*` bookkeeping of ours to get wrong, and writing a cookie and the session is a controller's job here. A language control has to survive scripting having gone wrong — it is what a reader reaches for when the page already makes no sense to them. `dropdown-top` keeps the menu clear of the mobile dock (`features/layout_test.exs`). The instance sets exactly two cookies (`_baudrate_key`, `locale`); theme and font size are `localStorage` and never reach the server — `doc/development.md` has the table an operator's privacy policy needs.
- **`BaudrateWeb.Helpers.local_path/2` is the one open-redirect guard.** Every controller that redirects to a path it was handed — the share target's stored `:return_to`, the language switcher's form field — asks there. It rejects `//host`, a scheme, `..`, backslashes, `@` and control characters. Do not re-implement it next to a new redirect; it lived in two places once and that is how one of them would have been fixed alone.
- **What a crawler is told is decided in two modules, and the sitemap invites only what a guest already sees** (ADR 0057). `Baudrate.Content.Sitemap` holds the one predicate — local (`user_id` not nil), not soft-deleted, `visibility == "public"`, in at least one board with `min_role_to_view == "guest"` — the same gate the syndication feeds and `Board.public?/1` use. A slug in a sitemap is an existence signal machines copy and repeat, and a URL in an index outlives the row it named, so four exclusions are deliberate and each reads like an oversight: **unlisted** articles (`visibility == "unlisted"` now also means `noindex, follow` on the page — the word in the composer promises it, and leaving one out of the sitemap alone promises nothing, because a sitemap is an invitation and not a gate), **member profiles** (`/users/:name` stays public and crawlable through every byline and is simply never *enumerated* — nobody opted into a machine-readable member list), **remote** articles, and anything in a board a guest cannot open. **Tag pages are in**, which is ADR 0055's forward reference honoured: alphabetically an inventory of tags is a sitemap, which is why it is not a page. **`noindex` and `Disallow` are not interchangeable** — a blocked page can still be indexed URL-only from its inbound links and its `noindex` is never read, so `robots.txt` blocks only `/ap/`, `/api/` and `/exports/` while `/search`, `/login`, `/register` and `/password-reset` stay crawlable and refuse indexing themselves. `robots.txt` is a **route**, not a file in `priv/static` (its `Sitemap:` directive needs an absolute URL), so it is deliberately absent from `BaudrateWeb.static_paths/0`. `BaudrateWeb.Crawlers` decides both directives and gives a `noindex` page **no** canonical, since the two contradict; `AuthHooks` assigns `canonical_url` on every `handle_params`, and the `<meta name="description">` is the `og:description` the page already computed (`OpenGraph.description/1`) so there is one description per page rather than two that drift. A page whose subject is missing answers **404, never a redirect** — a redirect tells a crawler the page moved, so it keeps asking and the target collects the authority of every wrong URL; this covers a **banned** account too (`BaudrateWeb.NotFoundError`, `plug_status: 404`), which must stay indistinguishable from one that never existed. **`test/baudrate_web/crawler_surface_test.exs` is the acceptance gate** — a new public surface goes in its indexable list or in its exclusion block, not in neither.
- **A search needs a scope, and relevance is the reader's own query.** `Baudrate.Content.SearchQuery` owns the `key:value` syntax — `parse/1`, `put/3`, `scoped?/1` — because two things write it: a reader typing, and the filter controls on `/search`, which set `board:`/`after:`/`before:` by **rewriting the query string** rather than carrying `?board=&from=&to=` of their own, so the box is the one description of the search and no control can silently disagree with it. `scoped?/1` is the rule: a query must name words, an `author:`, a `board:` or a `tag:`. A date range alone is refused, in `Content.Search` and not in the LiveView (the same function backs `/ap/search`, so a check at the page leaves the list reachable as JSON) — because newest-first it returns everything the viewer can see, which is ADR 0055's river arriving through the search box: *"a cross-board list of articles is a river whatever orders it, and filtering by reply count is mostly filtering by age"*. **`test/baudrate_web/no_content_ranking_test.exs` is the gate** — its fourth shape. `:sort` is `:relevance` (default), `:newest` or `:oldest`; ADR 0054 exempts search from the no-ranking rule precisely because *"the query and the ordering are the reader's"*, so no like, boost, comment or view count may ever enter an order clause here. **`/ap/search` pins `sort: :newest`** — an `OrderedCollection` is reverse-chronological by contract and a crawler's pages must not reshuffle when the site default moves. Two things every order clause keeps: a trailing **`id` tiebreaker** (tied `ts_rank` values plus OFFSET shows one row twice and drops another; `Content.Search.order_for/3` exists so a test can assert this structurally, because with a handful of tied rows the database is consistent anyway and only production is not), and **no `distinct`** in the query it orders — Ecto compiles `distinct: c.id` to `DISTINCT ON (c0."id")`, PostgreSQL requires those expressions to lead the `ORDER BY`, and Ecto prepends them, silently *replacing* the requested order. Comment search was written that way and returned oldest-first for its whole life while asking for newest-first; the board gate is an `exists` subquery now, which duplicates nothing. The **Users tab caps at 5 pages**: `Auth.search_users_page/2` is separate from `search_users/2` (four callers want a short list) and capped because ADR 0057 keeps a profile public and linked from every byline while refusing to *enumerate* the membership — uncapped paging walks it at a few hundred accounts a minute, including people who have never posted and so appear in no byline.
- **Account recovery is anchored outside the instance, and the member owns the anchor** (ADR 0058). **There is no email in this system** — no mailer, no address column — so recovery codes are the only self-service way back, and until 4D there was no way to mint more: `/profile/recovery-codes` read a session key nothing ever wrote, and `RecoveryCode`'s moduledoc claimed a TOTP reset re-issued them (it does not). `Auth.regenerate_recovery_codes/1` is the way out, behind the same step-up unlock as security keys. Past that the path is an admin, which is what a social engineer wants, so the admin is given something to *verify* rather than believe: a member registers an address **and an armored OpenPGP public key** from their own session, an admin confirms out of band that a signed message from that address checks out against that key, and only then can a reset link be issued. **Baudrate sends no mail, verifies no signature, parses no PGP and fetches no key from a keyserver** (that would be the third-party request ADR 0006 refuses, on a security path); the stored key is shape-checked, never validated, and `doc/sysop.md` carries the procedure because *no code enforces any of it*. Four rules hold it up and each looks like a restriction that could be relaxed: **a reset needs a verified contact** (otherwise the proof is optional and the old hole sits open beside it); **changing the address or key drops the row back to `pending`** (otherwise a stolen session is a permanent takeover — an admin can confirm an anchor and can never create one, and there is deliberately no function that does); **never an account at or above the issuer's own role level** (ADR 0029's rule; recovering an admin is the server console's job, which is now load-bearing ops documentation); and **clearing TOTP and security keys is a separate tick with its own audit line**, because "I lost my phone, take my 2FA off" must not ride along with the password. The token is stored as a SHA-256 only, single-use via one conditional `UPDATE`, and `/account-reset/:token` answers every failure identically and checks on submit rather than mount, so it is no oracle — and the path is `noindex` because the token is in it. The address is encrypted under the `:auth` keyring (ADR 0038), which is the **first secret column not in its owner's own row**: `Crypto.Rekey` targets now carry `owner_field`, and without it rotation would decrypt every member's address against the contact row's id and log them all undecryptable. **`test/baudrate/auth/account_recovery_test.exs` is the acceptance gate.**
- **The service worker caches the shell and never content, and its path is a string literal** (ADR 0059). It is registered from `app.js` on **every** page: it used to be registered by `PushManagerHook`, which mounts only on `/profile` and returns early when `meta[name="vapid-public-key"]` is empty, so an instance that never configured Web Push had no service worker anywhere and could not be installed — push availability and installability are unrelated questions that nothing in the admin UI connected. **Never write `~p"/service_worker.js"`**: it resolves to the digest-stamped name, so every deploy would register a *new* worker at a *new* URL and leave the old one controlling clients for ever, with no way to dislodge it; `phx.digest` keeps the undigested original, which is what makes the bare literal correct and preserves the same-URL byte-diff update check. Registration failures are swallowed — they reject routinely in private windows, over plain HTTP and under Selenium, and `features/js_errors_test.exs` fails the build on `console.error` and on an unhandled rejection. Exactly **two** things reach a cache: `/offline` and fingerprinted files under `/assets/` (immutable by construction, bounded to 60 entries); navigations are network-first and fall back only when there was no answer at all, since a 404 or a 500 is the server talking. Everything else gets no `respondWith`, which restores the browser's own path — the previous handler answered *every* request with a bare `fetch(event.request)`, adding a hop and caching nothing. **No article, comment, DM or board page is ever written to disk**: a cache on a forum is a record of what somebody read, on a device that may not be theirs alone, and "add offline reading" is the improvement this shape exists to refuse. `priv/static/service_worker.js` is a build output and is **not** tracked in git.
- **An edit is kept, and the history is public** (ADR 0060). Editing a comment writes a `comment_revisions` row holding the body **and the content warning** as they stood *before* the change — `article_revisions` gained the same two columns in the same migration, because removing a warning re-exposes what it hid and was the one edit leaving no trace. There is no grace window: a reply can arrive inside one, and then what it answered can be un-said underneath it. **The author alone may edit a comment** — not admins, deliberately narrower than `can_edit_article?/2` — because editing somebody else's words under their name is indistinguishable from their own, and deletion is already moderation's tool; it is enforced in `Content.update_comment/3`, at the context boundary, not only in the LiveView, and only `body`/`summary`/`sensitive` are castable (ADR 0049). **The `Update(Note)` names the current `ap_id` and nothing else**: `publish_comment_deleted/2` double-sends under `legacy_ap_id` because a `Delete` of an unknown object is a no-op, but an `Update` invites a dereference and a `#note-N` fragment resolves to the Person document — the failure ADR 0050 exists to end. An edit is **gated** like a publication (no `intent:`), so fixing a typo never carries a comment out of a board that does not federate. Inbound `Update(Note)` still writes no revision, as `handle_update_article/2` never has. `/comments/:id/history` refuses a **soft-deleted** comment (its revisions still hold every earlier draft, so serving them would make withdrawing a comment a way of publishing it) and a **remote** one, both 404 and never a redirect, and is `noindex` via a `/comments/` prefix in `Crawlers` — a prefix rather than an assign because `noindex_path?/1` is also what suppresses the canonical. **`test/baudrate/content/comment_revision_test.exs` is the acceptance gate**, with the federation half in `publisher_test.exs`.
- **An image description is not a form field** (ADR 0061, the sibling stage of ADR 0060). `Baudrate.Content.ImageAlt` owns the rule for all three image tables and federates as the attachment `name`; `article_images`, `comment_images` and `timeline_item_reply_images` each carry `alt`. Uploads are `auto_upload: true` with a `progress:` callback, so **the row exists before the composer is ever submitted** — the description therefore saves itself against that row (`phx-blur` + a debounced `phx-keyup`, `phx-value-id`), carries **no `name` attribute** so it never joins the form params, and sits in a `phx-update="ignore"` container so the `phx-change` re-render on every keystroke elsewhere cannot patch it back and erase what was typed. Rendering: a gallery image is always inside an `<a>`, so **the link carries the description via `Helpers.image_link_label/2` and the `<img>` is `alt=""`** — text in both announced the same image twice. An empty description normalises to `nil`, never `""`: in HTML `alt=""` means "decorative, announce nothing", which for a photograph somebody chose to post is a lie. `ImageAlt.from_remote/1` strips tags and bounds a peer's `name` at ingest — it was extracted and then **discarded** for want of a column, so a described remote image still rendered `Image 2`. **Remote images arrive by two routes and only one is a row:** an image on a remote *article* becomes an `article_images` row with `alt`, while one on a remote *comment* or DM is appended to `body_html` as an inline `<img>` by `InboxHandler.append_attachment_images/2`. That second route cannot pick a fallback at ingest — a translated string would freeze the ingest process's locale into the stored row — so `BaudrateWeb.ImageAltFallback` fills an empty or missing `alt` at **render**, inside `SafeHTML.body_html/1`, the same shape and for the same reason as `Media.Rewriter`: it covers every row written before it existed, with no backfill. `image_alt_coverage_test.exs` fails the build if a composer renders an image upload without `<.image_alt_input>`; an avatar is the one exemption, because its accessible name is the display name.
- **The federated `updated` field means an edit happened, and it asks the revision table.** `ObjectBuilder.article_object/1` and `comment_object/1` emit `"updated"` only when `Content.article_edited?/1` / `comment_edited?/1` says a revision exists; the *timestamp* published is still `updated_at`, which is the right value once an edit is known. It used to be derived from `updated_at` being more than five seconds past `inserted_at` — a proxy, and the proxy broke: the v1.31.0 `ap_id` backfill rewrote rows with an ordinary changeset months later, so every comment it touched federated as edited on the day of the backfill while this site's own history page, which counts revisions, said it had never been edited. Mastodon shows an "edited" badge whenever `updated` differs from `published`, so the field has to mean an edit and nothing else. **Never re-derive it from a timestamp** — any housekeeping write moves one. `Release.backfill_ap_ids/1` now also forces `updated_at` back, because a repair pass is the write that most wants to be invisible to "when did this last change". `object_builder_test.exs` carries the regression for both builders and `release_test.exs` for the backfill.
- **The door is defended by work, not by a third party** (ADR 0063). **Registration costs a proof-of-work solve**, self-hosted because a hosted CAPTCHA is a third-party subresource on the one page every new member loads (ADR 0006), and applied in all three registration modes. `Baudrate.Auth.Challenge` issues a nonce and verifies one SHA-256; `assets/js/challenge_solver.js` finds the answer, in a **same-origin worker loaded by the bare literal `/challenge_worker.js`** — `worker-src` is `'self'`, so a `blob:` worker will not run, and `~p` would digest-stamp the name (ADR 0059) — with a main-thread fallback. The challenge lives in `RegisterLive`'s assigns and is **re-issued after every attempt, success included**: a consumed challenge left as `nil` reads as "switched off", and one solve would then register any number of accounts on a crafted socket. A submit that beats the answer is **held server-side** and completed when it lands; the button is never disabled. The default is **18 bits and the cap 22**, from a measured desktop rate (~1.3 M hashes/s in V8, ~0.9 M in Firefox) and an *estimated* phone eight times slower — 20 bits is then about seven seconds on a phone, 24 nearly two minutes. The phone column is still unmeasured; a Pixel 8a at 20 bits answered before its owner finished the form (2026-09-22), because the solve runs while the form is being filled in. The hook records which path answered in a *child* of its `phx-update="ignore"` container, because LiveView still re-syncs an ignored element's own `data-*` attributes on every patch. The test suite runs with `registration_challenge_bits: 0` (`config/test.exs`); tests about the challenge turn it on. **IP and CIDR bans** (`Baudrate.Auth.IpBans`, the only write path, which refreshes `IpBanCache` itself) refuse **registration and sign-in and never reading**. Sign-in is checked in `LoginLive` before the password is tested, and again in `SessionController`'s **`establish_session/3`, the one function every sign-in path ends in** — the backstop a new path cannot route around. Four refusals, each of which looks relaxable and is not: a private or loopback range (what every visitor looks like when the proxy is misconfigured — `HTTPClient.private_ip?/1`, both ends), anything broader than `/8`/`/16`, a range holding the acting admin's own address (or any range when that address is unknown), and a broad range without a second tick. Expiry is **decided by the clock at read**, and the cache holds expired rows too. **Banning an invite chain** intersects the client's ticked ids with a tree the context recomputes (`Auth.ban_invite_chain/4`), authorizes each account separately, and **skips an account already banned**, because re-banning overwrites its `ban_reason`. Acceptance gates: `registration_challenge_test.exs`, `ip_ban_test.exs`, `invite_chain_ban_test.exs`, and `features/registration_challenge_test.exs` for the solver against the server.
- **A new account is slowed down, not shut out** (ADR 0064). Until an account is `new_account_days` old *and* has `new_account_posts` articles and comments still up (3 and 3; 0 and 0 turns it off), it may put **one external link and one image** in a post, post **ten times an hour** across articles, comments and timeline replies together, DM only people who **follow it, wrote to it first, or are staff**, and add **no link or image to its signature** — which renders under every article it posts (`Trust.check_signature/3`, judged against the *stored* signature). The bio and profile fields render as plain text everywhere and need no limit. `Baudrate.Auth.Trust` decides this **from the clock and a count every time it is asked — never a stored flag**, for ADR 0029's reason, so trust also *leaves* with the posts that earned it. Bots are exempt **inside the predicate** (an RSS item carries several links; ADR 0031's finding), admins and moderators by role, and an invite confers nothing. Timeline replies do not count toward trust — no moderator here can remove one. **`Auth.check_post/4` sits beside `ensure_can_interact/1` at every posting function, and edits are the second way in**: an edit may not add a link or raise the image count past the limit, and never has to remove what is already there. The hourly bucket (`RateLimits.check_new_account_post/1`) is taken inside `check_post/4`, not in a LiveView, so a new posting path cannot forget it. The **article edit page attaches an upload to the live article as it lands**, so it goes through `Content.authorize_article_image/2` / `add_article_image/3` — before this it skipped both gates. **Links are counted as a browser resolves them**: `HtmlParser.Native.extract_urls/2` joins each `href` to the origin with the `url` crate and compares *hosts*, because `//host`, `/\host` and `http:host` all leave the site and a prefix check saw none of them (it also took `https://ours.example.spam/` for ours); `extract_first_url/2` is the first of the same list. A DM refusal reports the recipient's own `dm_access` first, and every refusal goes through `Helpers.refusal_message/3`, which names the limit and what is left. The test suite runs with the limits off (`config/test.exs`); **`test/baudrate/auth/trust_test.exs` is the acceptance gate — a new way to post goes in it.**
- **What waits for review is not content yet** (ADR 0065). A held post is a row in `held_posts` (`Baudrate.Moderation.HeldPosts`), **never an article or comment with a flag**: nothing chokepoints the listings, and a `held_at` column would have to be excluded by hand from every one — the shape that leaked twice. **Only a composer can hold**: every LiveView that writes calls `Content.submit_article/3` / `submit_comment/2`, which return `{:held, %HeldPost{}}` for a new account's first `hold_first_posts` posts (the count trust is earned by; staff and bots never; 0, the default, is off) or a post a `hold` filter matched; `create_*` never hold, and `test/baudrate/content/submit_path_test.exs` fails the build if `lib/baudrate_web` calls them. A held post has already passed the sanction gate, a filter's `block` and the limits on new accounts. **Approval is publication**: `HeldPosts.approve/2` replays `create_*` as the author with `held_post:`, whose first Multi step deletes the pending row, so a second approval rolls back instead of publishing twice; it re-checks the author's standing first, then boards (a lost one is dropped) and the thread, and takes no hourly place. A board moderator reviews only what is wholly inside their boards (P1-D5), at `/moderation/held`. A rejection keeps the text 90 days; the orphan image sweeps spare a **pending** post's uploads. **Filters** (`Baudrate.Moderation.ContentFilters`, not `Content.Filters`) are a `word`, `substring` or `domain` — **never a regular expression** — matched in linear time over text in one normal form (NFKC, `\p{Cf}` stripped, lower case) and **as a reader sees it** (rendered, tags stripped), with links resolved by `extract_urls/2`. They run beside `ensure_can_interact/1` at create **and edit** (an edit is judged by what it adds), on timeline replies, and in `InboxHandler` on every route remote content arrives by (`Create`, `Update`, `handle_announce_object/3`); a hold becomes a flag where nothing can be held, an edit is refused instead, remote content is only dropped (answering `:ok`) or flagged. **Screen everything that is stored and shown, and decide an exemption by what is stored, never by what the incoming object claims** (ADR 0066, amending 0065's decisions 8 and 13): the v1.39.0 audit found `source.content`, poll options, attachment and image descriptions all carrying text past the filter, and an `Update(Note)` exempted because it was *addressed* like a message while the handler rewrote a public comment by its `ap_id`. A description changed on a published image passes the sanction gate and the filters (`Images.set_alt`), and `ObjectResolver.resolve/1` (import by URL) screens and is rate limited. **Direct messages are never screened.** A refusal (`:content_filtered`) never names the pattern; every match is a `content_filter_matches` row without its text; a flag is a report with `content_filter_id`. **`test/baudrate/moderation/content_filter_test.exs` and `held_post_test.exs` are the acceptance gates — a new way to post goes in the first.**
- **A draft is kept in two places, on purpose** (ADR 0062). The composer's `localStorage` hook and a `article_drafts` row both autosave, and **neither replaces the other**: the hook is the only half that works with the socket down, and the row is the only half that follows a member to another device. Deleting either looks like a simplification and is a regression. A fresh `/articles/new` restores the most recent draft and the hook then fills only fields that are *still empty*, so the two cannot fight. **Three refusals**: a composer opened from the PWA share target (the shared post would be buried), one opened from a board (an unrelated draft is a non-sequitur), and an empty draft (the residue of opening the composer). A draft is **not content** — no `ap_id`, no listing, no federation, no view for staff — and every read is scoped by owner *in the query*, with another member's id answering as a miss rather than a refusal. The cap is a `COUNT` at save time following `Invites.invite_quota_remaining/1`, never a stored counter, and it bounds **creating** a draft only, so a member at the limit can still type into the composer they have open. **The orphan image sweep must spare an image a draft holds** (`Images.delete_orphan_article_images/1`): an upload belongs to no article until the post is submitted, which is exactly what a draft preserves, so without it a post drafted overnight is resumed with its pictures already unlinked. Boards and images are re-checked at *resume*, never trusted from the row. **`test/baudrate/content/draft_test.exs` is the acceptance gate.**
- **A visitor's own instance is discovered, not guessed** (Phase 4E). `Baudrate.Federation.RemoteFollow` reads the `http://ostatus.org/schema/1.0/subscribe` template out of the *visitor's* WebFinger document, because Mastodon, Akkoma and Misskey each use a different path. Both inputs are somebody else's: the domain is typed by a guest, so `Discovery.webfinger_document/3` passes **`refuse_blocked: true`** (ADR 0030 decision 9 — the flag was missing from `webfinger_lookup/3` and was covered only because `ActorResolver` re-checks downstream, which this flow has no equivalent of); the template comes from that domain, so it must be HTTPS, contain `{uri}`, and sit **on the host the visitor typed**, or a hostile server answers WebFinger with a link to anywhere and we render it. The form carries a **kind and a name, never an actor URI** — the controller rebuilds it and re-checks, and a board must satisfy `Board.federated?/1`, not the `ap_enabled` its own handle is guarded on, or the visitor gets a handle whose actor 404s and whose `Follow` is `Reject`ed (ADR 0004/0043). It **renders a link and never redirects off-site**: nothing else in `lib/` calls `redirect(external:)`, `local_path/2` exists to refuse anything leaving the site, and a link lets the visitor read the destination host first. Every failure renders one page naming no server. **`test/baudrate/federation/remote_follow_test.exs` is the acceptance gate.**
- Settings are cached in ETS via `Baudrate.Setup.SettingsCache` (ADR 0014, with boards and domain blocks); `set_setting/2` auto-refreshes the cache on success, and writing `ap_federation_mode` / `ap_domain_allowlist` also refreshes `Federation.DomainBlockCache`, which every federation domain check reads. Direct DB writes to the `settings` table must call `SettingsCache.refresh()` (and `DomainBlockCache.refresh()` for those keys) manually; before v1.18.2 a block from the Federation dashboard was ignored until the next settings save or restart.
- **A blocked domain is a row in `domain_blocks`, not a setting** (ADR 0030). `Federation.DomainBlocks` is the only write path and refreshes `DomainBlockCache` itself; `DomainBlockCache` is still the only read path for the per-activity check, and **allowlist mode deliberately still reads `ap_domain_allowlist`** — an allowlist is configuration about who may reach us, not a record of moderation decisions. Each block carries `reason`, `public_comment` and `blocked_by_id`, and unblocking is a row delete. `DomainBlock.normalize_domain/1` reduces a pasted URL or `@user@host` handle to a bare downcased host, and blocking this instance's own domain is refused. Do not reintroduce the comma-separated `ap_domain_blocklist` setting, and do not parse a domain list anywhere else.
- `remote_actors.domain` is stored **downcased** (`RemoteActor.changeset/2`). It is written from the host of the peer-supplied `ap_id`, and the domain-block filter compares it with SQL equality, so an actor stored as `Example.COM` would otherwise stay visible under a block on `example.com`.
- Boards are cached in ETS via `Baudrate.Content.BoardCache`; board mutations in `Content` (`create_board`, `update_board`, `delete_board`, `toggle_board_federation`) auto-refresh the cache. Settings cache is disabled in tests via `settings_cache_enabled: false`; board cache runs normally in tests.
- **No third-party subresources, and one click-to-load exception** (ADR 0006, refined by ADR 0045). A page must never emit an `<img>` (or any other subresource) pointing at a host we do not control — that discloses every viewer's IP, User-Agent, and reading times to every remote instance whose content is on the page. CSP enforces this with `img-src 'self' data: blob:`. Any remote image URL — federated attachments, remote actor avatars, timeline-item attachments, RSS/bot article bodies, user Markdown — must be passed through `Baudrate.Media.Proxy.url/1` (templates) or `Baudrate.Media.Rewriter.rewrite_img_src/1` (stored HTML). Use `BaudrateWeb.SafeHTML` instead of a bare `raw/1` for stored content — `body_html/1` for an HTML column, `markdown/1` for a Markdown one; it applies the rewrite, which is what covers rows written before the proxy existed with no backfill. **Both entry points matter**: eleven sites rendered a Markdown column without either, the article body among them — ten with a bare `raw(Markdown.to_html(...))` and one that built the HTML in the LiveView and wrote `raw(@assign)`. Nothing hotlinked, because `to_html/1` carries the proxy rewrite itself — but it cannot carry the translated `alt` fallback of ADR 0061, so the article body would have kept skipping undescribed images while comments stopped. `rendered_html_passes_test.exs` fails the build on a bare one. `test/baudrate_web/no_hotlink_test.exs` is the acceptance gate, and it covers every subresource element — not just `<img>`, which is how a YouTube `<iframe>` sat on article, comment and DM pages unnoticed. **The one embed is click-to-load**: the server renders a local poster and `YouTubeEmbedHook` builds the `<iframe>` on the reader's click, so scrolling past a video contacts nobody. Keep `phx-update="ignore"` on its container or a PubSub patch kills a playing video, and keep `frame-src` at exactly `https://www.youtube-nocookie.com` — the gate asserts it, so a second embed origin fails the build and needs its own ADR.
- Media proxy (ADR 0006): `GET /media/:sig/:encoded` (`BaudrateWeb.MediaController`) serves an HMAC-signed remote URL from a local WebP re-encode. Signing is deterministic — HMAC over the URL only, never `Phoenix.Token` (its embedded timestamp would mint a new `src` on every render, defeating browser caching and generating a LiveView diff for every avatar on every patch). It is not an open proxy: only URLs this instance emitted can be requested. Cache lives at `priv/static/uploads/media_cache/<sha256>.webp` — that path is forced by ops (systemd `ReadWritePaths` covers only `shared/uploads`), and nginx denies it directly so the signature cannot be bypassed. Failures negative-cache for 1h and redirect to `/images/media-unavailable.svg`.
- Link previews: async fetch of OG metadata after content save (first URL only). Images are proxied server-side (re-encoded to WebP via libvips). The `link_previews` table is shared/deduplicated by URL hash. Preview cards render via `<.link_preview>` component in `core_components.ex`. Stale previews (>7 days) are refreshed hourly by `SessionCleaner`; orphans (>30 days, no FK refs) are purged.
- AP visibility: articles, comments, and timeline items have a `visibility` field (`public`, `unlisted`, `followers_only`, `direct`) derived from `to`/`cc` addressing on ingest via `Federation.Visibility.from_addressing/1`. Local articles and comments accept only `public`/`unlisted` (their changesets reject the rest): board content is public on this site whatever its addressing, and DMs are the private channel. Remote rows keep all four values. Forwarding permissions respect visibility: only `public`/`unlisted` content is forwardable by non-author/non-admin users.
- Bot accounts: users with `is_bot: true` cannot log in — `authenticate_by_password/2` rejects them. Bot users have `dm_access: "nobody"` and a locked random password. Managed exclusively via `Baudrate.Bots` context and the `/admin/bots` admin UI.
- `published_at` on articles: stores the original publication timestamp from RSS/Atom feed entries (via bot posting). Nil for locally-created articles. Used to preserve original feed entry dates when bots create articles.
- **LiveView resets form inputs to their rendered value on every re-render.** When `phx-change` (or any assign used inside the form) re-renders a form, each input is patched to the `value` the server rendered. An input with no `value`, a `value={@assign}` the handler never updates, or a textarea filled from stored data loses what the user typed. This erased the current password on `/profile/password` and the username and recovery code on `/password-reset` as soon as the new password was typed, and a typed bio in the `/admin/bots` form. `phx-change` works only on a form or an input, never on a `<fieldset>` or `<div>`: the composers' poll fieldset had one, so poll edits arrived as the article form's change, which dropped them, and typing the title erased every option (use `PollComposer.assign_poll_params/2`). Fix: the change handler assigns the params back (`to_form(params, as: ...)`) and every input renders `value={@form[:field].value}`; inputs the server must never patch (bot profile field rows) go in an `id` + `phx-update="ignore"` container. LiveView tests do not patch a DOM, so assert the value is rendered back after `render_change/2`. The browser crawl (`js_errors_test.exs`) types into every `phx-change` form field by field and fails when a field is erased.

### CI

- **CI runs only in the project's CI images** (ADR 0027, ADR 0036, `ci/image/`): `baudrate-ci` for tests and `baudrate-build` for the release, two targets of one Dockerfile on **production's Debian release** (`debian_version` in the Ansible inventory), because a release carries its own Erlang runtime and NIFs linked against the system that built it. Jobs use the digests in `ci/image/image.lock` and `ci/image/build-image.lock` after `ci-image-ref.yml` verifies their provenance attestations. Never add a third-party action, `curl | sh`, or an unpinned download to a workflow: put the tool in `ci/image/Dockerfile` with a SHA-256 cross-checked against upstream's published checksum. Use only GitHub-owned actions, pinned to a commit SHA with a `# vN` comment. Bumping Erlang/Elixir (`.tool-versions`), esbuild/Tailwind (`config/config.exs`) or Selenium/GeckoDriver also needs the Dockerfile `ARG`s and checksums updated; CI's `verify-toolchain.sh` fails until the image is rebuilt and the proposed `image.lock` change is merged.
- **CI tests production's PostgreSQL major version, server and client both.** Production is Debian 12 with PostgreSQL 15, while development machines and Debian trixie run newer versions. The version is set in three places that `verify-toolchain.sh` holds together: `postgres_version` in `ansible/inventory/group_vars/all.yml`, `POSTGRES_MAJOR` in `ci/image/Dockerfile` (the client, which Debian 12 ships), and the digest-pinned `postgres:<major>` service images in `elixir.yml` and `release.yml`. The client matters as much as the server: `pg_dump`/`pg_restore` 17+ write `SET transaction_timeout`, which a 15 server rejects, so a newer client fails the backup restore test against a correct backup. Do not "upgrade" CI's PostgreSQL ahead of production. SQL that needs a newer server (`MERGE … RETURNING`, `JSON_TABLE`, `any_value()`) passes on a development machine and fails in CI, which is the point.

- **CI builds, smoke-tests and attests the release; the deploy builds it on the server** (ADR 0036, then ADR 0037). Publishing a GitHub release starts `release.yml`: a read-only build job runs `ci/release/build.sh` and `ci/release/smoke-test.sh`, and a separate publish job attests the tarball and attaches it to the release, for installing by hand. The same build and smoke test run on every push, so do not let the Release build job go red — it is the gate that catches a release that cannot start. The Ansible deploy clones the tag and builds it on the server: v1.26.0 installed the tarball instead, and moving 46 MB down from GitHub and up to the server cost 13 minutes against 2 for an incremental build, so ADR 0037 reversed that one decision. Do not make the deploy depend on the artifact again without solving the transfer (a registry pull on the server is the open option). `rollback-baudrate.yml` restores a kept release and refuses when the database has migrations it does not know.
- **The cookie inside a release is public** (ADR 0036, unaffected by ADR 0037). `mix.exs` fixes it to a placeholder and `rel/env.sh.eex` refuses `start`/`remote`/`rpc`/`stop` with it or without `RELEASE_COOKIE`; Ansible generates a cookie per server into `env/release_cookie`. Distribution listens on `127.0.0.1` only (`rel/*.vm.args.eex`, node `baudrate@127.0.0.1`). Never ship a real cookie in the release or loosen the loopback binding: the production host runs another application under another account.
- **Every Sobelow finding fails CI** (`.sobelow-conf`, Security checks job). Fix it, or — after checking that, say, a file path is built by the server and never from request input — mark that function with `# sobelow_skip ["Check"]` directly above it. Never use `--mark-skip-all` (its fingerprints include line numbers). `mix deps.audit` reads the advisory list baked into `baudrate-ci`; it must not fetch at run time.

## Project Conventions

### Principle Maintenance

- Ensure this document is updated to reflect any changes in the workflow and maintain consistency.

### While Planning, Refactoring & Doing Code Review

- When a feature requirement is unclear or ambiguous, seek clarification on definition and scope rather than guessing.
- Each implementation should match specs, open standards, industry standards, and common practices.
- Follow ActivityPub specification

### While Coding

- **Always** consider responsiveness and accessibility for UX/UI; follow the WAI-ARIA specification.
- **[TOP PRIORITY a11y] Every meaningful element in every page template MUST carry a stable, semantic `id` and/or `class`** so any element can be located precisely (for accessibility tooling, testing, and styling). This is a first-class accessibility requirement, not optional polish. Convention:
  - **Coverage** — annotate region/section containers, all interactive elements (buttons, links, inputs, selects, textareas, toggles), every loop-rendered list/table/card item, and key content nodes (headings, labels, values, empty states, error/preview blocks). Skip purely presentational layout wrappers (bare `flex`/`grid`/spacer divs) and leaf presentational components (`<.icon>`).
  - **Naming** — simple kebab-case, page/section-prefixed (no BEM `__`): `id="profile-bio-section"`, `class="profile-bio-label"`, `class="profile-bio-value"`.
  - **Uniqueness** — `id` must be unique per rendered page; loop (`:for`) items MUST derive a dynamic id from the record (`id={"muted-user-#{mute.id}"}`) plus a shared stable `class` (`class="muted-user"`).
  - **Non-destructive** — only ADD `id`/`class`; never remove or reorder existing Tailwind utilities, `phx-*`, `aria-*`, `data-*`, `:if`/`:for`, or `gettext()`. Put the semantic class first, utilities after.
  - **Stylesheets target the semantic selectors** — custom CSS in `assets/css/app.css` (theme layers, focus styles, component tweaks) MUST hook onto the semantic `id`/`class` selectors, not fragile structural/positional selectors (`.card > .card-body > .card-title`, `:nth-child`, tag chains). When you add or change a style rule, its selector must correspond to a meaningful element's semantic `id`/`class`; if that element lacks one, add it first. This keeps styling stable against markup refactors and keeps the selector's intent self-documenting. **`test/baudrate_web/semantic_anchors_test.exs` is the acceptance gate** for the two halves of ADR 0018 that can be falsified: `app.css` gains no structural or positional selector (the two daisyUI `.dropdown` component rules are named exemptions — a third is a decision, not an edit), no page in `@public_pages` renders a duplicate `id`, and no `:for` element carries a literal `id` (which would render one id per item). The headline rule — that every *meaningful* element carries a semantic handle — is deliberately **not** gated: "meaningful" is a judgement, and 23 of 118 `:for` elements legitimately carry no class, so an approximating check would fail the build for correct code. The Aqua themes' `.card > .card-body` rules are out of scope for the same reason they always were: they restyle a daisyUI component, not an element with a handle to use.
- **A semantic `id` can still be the wrong `id`: content blockers hide elements by name.** `#policy-accept` was `display: none !important` for every member running uBlock Origin with the annoyances/cookie lists — the selector sits in a public cosmetic-filter list next to `.alert.ccpa-message` and `.fixed.cookies_law`, because "policy…accept" is what a cookie-consent bar looks like. The element rendered correctly, passed every LiveView and browser test, and was invisible in the browsers that matter. **Never name a control with `accept`, `consent`, `cookie`, `gdpr`, `ccpa`, `banner`, `promo`, `popup`, `overlay` or `sponsor`** — the site's own notices use `-notice` (`terms-notice`, `data-export-notice`, `account-move-notice`) and its agreement control is `terms-agreement`. This bites hardest where a hidden control is a dead end: a member who cannot see the accept card cannot post and is told nothing, and a hidden `account-move-notice` would deny a hijacked account the warning ADR 0025 relies on. `test/baudrate_web/features/terms_accept_test.exs` asserts the control is *visible*, not merely present — but no test can see a blocklist, so the naming rule is the real defence.
- **Use HTML5 semantic elements** — `<section>` with `aria-labelledby` for headed content areas, `<article>` for self-contained content items in lists, `<aside>` for supplementary content, `<nav>` for navigation. Assign semantic `id` attributes to content containers and unique `id` + semantic CSS class to each list item.
- **Never use bare English strings for user-visible text** — always wrap in `gettext()`. This applies to flash messages, template text, feed metadata, HTML attributes like `title`, and any other text shown to users. Use `gettext()` with `%{var}` interpolation (not string interpolation) for dynamic values. Shared translation helpers (e.g. `translate_role/1`, `translate_status/1`) belong in `BaudrateWeb.Helpers`.
- **Always** keep i18n strings in sync across locale. `test/baudrate_web/translation_coverage_test.exs` fails the build on an empty `msgstr` in zh_TW or ja_JP (`en` is exempt: its `msgid`s are the source text Gettext falls back to). A string whose translation really is the English — an example value in a placeholder — gets written out in full with a translator comment saying so; an empty entry cannot be told from an oversight.
- **Locale display names are autonyms, and `zh_TW` is 台灣漢語** — never 繁體中文 and never 正體中文, both of which name a *script* and frame the variety as a typographic variant of something else. `doc/eua.md` and `doc/privacy-policy.md` name 台灣漢語 in their governing-language clauses, so a switcher that disagreed offered a reader a different thing from the one the terms are written in. The Gettext *locale code* stays `zh_TW`; this is the human-readable name only.
- **`mix gettext.extract --merge` silently mistranslates.** Its fuzzy matcher attaches an existing translation to any new `msgid` that looks similar, and the report only says "N reworded (fuzzy)" — the `.po` file gets a plausible-looking wrong translation, not an empty one. Real examples: "Your account is suspended." came back as zh_TW for *"your account is pending review"*, "Registration refused." as *"registration mode"*, and "Failed to post comment." as *"failed to delete comment"*. So after every merge, **check every newly added `msgid`** (`git diff priv/gettext/default.pot | grep '^+msgid'`), not just the ones left with `msgstr ""`.
  - **`en` is not safe from this either**, which is the half that went unnoticed for months. Its entries are *supposed* to be empty so Gettext falls back to the `msgid` — but the fuzzy matcher writes into `en` like any other locale, and **Gettext serves a fuzzy translation exactly like a reviewed one**. Six English strings were rendering somebody else's sentence: `Published` came out as "Push", `Remote actor not found.` as "Remote actor", `liked your comment` as "liked your article", and "N earlier messages loaded" as "N unread messages". **Three of the six were not even marked fuzzy** — a past merge wrote them and the coverage test exempts `en`, so nothing looked. The fix is always to **blank the `msgstr`**, never to retype the English: a corrected copy is a second place the source text lives. `translation_coverage_test.exs` now fails the build on any `en` entry whose translation differs from its own `msgid`.

### Branching

- **All development happens on the `current` branch.** Commit and push every change (features, fixes, docs, dependency bumps) to `current`.
- **Never commit to, push to, or rebase `main` directly.** `main` only moves when a release is cut, by merging `current` into it (see Release Engineering). If you find yourself on `main` with changes, `git switch current` before committing (uncommitted changes carry over).
- Because `main` is never touched directly, the release merge is always a fast-forward (`git merge --ff-only current`). If it is not, stop and ask — something was committed to `main` out of band.

### Release Engineering

When creating a new release (on `current`):

1. Update `CHANGELOG.md` with the new version entry (follow [Keep a Changelog](https://keepachangelog.com/) format)
2. Update `version` in `mix.exs` to match the new tag version
3. Commit the release on `current` and push `current`
4. Merge into `main`: `git switch main && git merge --ff-only current && git push origin main`, then `git switch current`
5. Create the annotated git tag on the release commit (e.g. `v1.1.21`) and push it (`git push --tags`)
6. Create the GitHub release via `gh release create`. Publishing it starts `release.yml`, which attests the tarball and attaches it for installing by hand (ADR 0036). Since the deploy builds on the server (ADR 0037) it does not need that tarball, so this run does not gate the deploy — but read its result, because a red build means the release could not start in CI. What gates the deploy is `elixir.yml` on the release commit, whose Release build job runs the same build and smoke test

### Security Rules

- Never use `String.to_atom/1` on user input
- Never put user input in file paths
- Validate at system boundaries (user input, external APIs, federation)
- All federation content is HTML-sanitized before storage
- SSRF-safe remote fetches (HTTPS only, DNS-pinned, redirects revalidated per hop). `HTTPClient.private_ip?/1` is the single deny-list: private/loopback/CGNAT/link-local/multicast/reserved, the non-routable IPv4 special-purpose ranges (`192.0.0.0/24`, `192.0.2.0/24`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`), and the IPv6 documentation/discard prefixes. **Every IPv4-over-IPv6 tunnel prefix decodes its embedded address and re-checks it** — `::ffff:0:0/96`, `64:ff9b::/96`, `::a.b.c.d`, and `2002::/16` (6to4). Teredo (`2001::/32`) obfuscates the embedded address instead of carrying it plainly, so the prefix is refused outright rather than decoded. When adding a range, add it here and nowhere else.
- Outbound response bodies are capped **while streaming**: `HTTPClient.build_pinned_opts/3` installs an `into:` collector that halts the connection as soon as the received bytes or a declared `content-length` exceed `max_payload_size` (GET and POST alike), and sets `request_timeout` (whole-request deadline, default 60 s) alongside the per-read `receive_timeout`. Checking `byte_size(body)` after the fact buffered attacker-sized bodies in RAM first, and a per-read timeout alone let a byte-every-29-seconds trickle pin a delivery job forever. `compressed: false` keeps the cap on wire bytes.
- Rate limit all public endpoints
- File uploads: validate magic bytes; avatars are re-encoded as WebP (EXIF stripped)
- Federation private keys encrypted at rest (AES-256-GCM via `KeyVault`)
- Content size limits: 256 KB AP payload, 64 KB content body
- Inbound remote actor public keys must be RSA ≥ 2048 bits (`HTTPSignature.validate_public_key_pem/1`). Enforced at **both** `ActorResolver` ingest (so a weak key is never cached) and signature-verification time (so keys cached before the check are rejected too). Non-RSA keys return `:unsupported_key_type` — `verify_signature/3` only does `rsa-sha256`, so they could never have verified.
- `INSTALLATION_KEY` is **required in production until setup completes**: `EnsureSetup` answers 503 on every browser route while setup is incomplete and no key is configured, and `SetupLive.mount/3` carries the same gate for the websocket. Never move this to a `raise` in `runtime.exs` — that runs before the Repo starts, so it cannot know whether setup completed, and a boot-time raise turns a transient DB outage into a bricked instance.
- `RealIp` is fail closed: an unconfigured `trusted_proxies` means loopback only, and `[]` means trust nobody. Never restore a trust-everything branch — a spoofable `x-forwarded-for` defeats every per-IP rate limit and poisons the `ip_address` audit trail. Widen trust with a CIDR entry via `BAUDRATE_TRUSTED_PROXIES`. The prod endpoint binds the IPv6 any-address, so an IPv4 peer (nginx on `127.0.0.1`) arrives as `::ffff:127.0.0.1`. `RealIp.unmap_ipv4/1` normalizes the peer, the forwarded address and allow-list entries before any comparison. Without it the loopback proxy never matched, and every visitor shared one rate-limit bucket and one logged IP (the pre-v1.15.0 production state). Unmap **only** `::ffff:0:0/96`: NAT64/6to4 are different hosts, and decoding them would widen trust. Resolve client IPs only through `RealIp.client_ip/2` (plug) or `Helpers.extract_peer_ip/1` (LiveView), never from raw `peer_data` or header values.
- Remote actor display names **and `preferredUsername`** sanitized via `Federation.Sanitizer` (strip HTML, strip C0/C1 controls **and Unicode bidi overrides**, truncate — 100 chars for display names, 64 for usernames). The username is the identity anchor the UI renders as `@username@domain`, and it is also the display-name fallback when the actor publishes no `name`, so it needs the same treatment. Zero-width joiners (U+200C/200D) are deliberately kept — they are load-bearing in emoji sequences and Indic/Persian scripts. `sanitize_username/1` returns `nil` for anything that sanitizes to nothing, so `ActorResolver` falls back to deriving the handle from the actor `id`.
- Every remote-controlled string that reaches a column needs an explicit bound. `content` is covered by `Validator.validate_content_size/1`, but `name`, `summary`, `attachment` values, and `alsoKnownAs` are not — they are truncated at ingest in `ActorResolver` / `InboxHandler` with a `validate_length` backstop in the changeset. `Content.TitleDeriver.truncate_title/2` treats `max_len` as a **hard ceiling including the ellipsis**: counting the "…" on top would push a 255-grapheme CJK title to 256 and fail the `:title` validation on both `Article` and `TimelineItem`, silently dropping the inbound object.
- Follow OWASP Top 10 to audit common security vulnerabilities

## Testing

- **Always use seed 9527 and 4 partitions** when running the full test suite
- **Running the suite against another PostgreSQL server** (e.g. production's major version in a container on port 5433): set `PGHOST` and `PGPORT`, which `config/test.exs` passes to the Repo. Before that change, `PGPORT` in the environment reached raw Postgrex connections (lock-holder tests, `ecto.create`) but not the Repo, so one run silently spread across two servers and failed in confusing ways. Confirm with `SELECT version()` from the Repo, not from how the databases got created. The backup restore test also needs a client of the same major version on `PATH` (see the CI bullet).
- **Always run the full test suite without asking** — never ask for permission to run tests
- `use BaudrateWeb.ConnCase` for LiveView/controller tests; `use Baudrate.DataCase` for context tests
- `setup_user("role_name")` — creates a test user with the given role (seeds roles if needed)
- `log_in_user(conn, user)` — authenticates a connection with session tokens
- `log_in_admin(conn, user)` — authenticates an admin with TOTP sudo mode enabled (sets `admin_totp_verified_at`)
- `errors_on(changeset)` — extracts validation errors as `%{field: [messages]}`
- Rate limiter stubbing: tests use `BaudrateWeb.RateLimiter.Sandbox` — call `set_global_response({:allow, 1})` to bypass rate limits, or `set_fun(&BaudrateWeb.RateLimiter.Hammer.check_rate/3)` for the real Hammer backend. Tests that use the real backend must reset state with `BaudrateWeb.RateLimit.reset_all/0` in setup (Hammer 7 dropped v6's `Hammer.delete_buckets/1`).
- **JS hooks are only tested in the browser.** After changing `assets/js/` or a template's `phx-hook`/hook-driven events, run `mix test --include feature test/baudrate_web/features/js_errors_test.exs` (crawls pages, fails on JS errors, `console.error` and LiveView crashes). A hook's `pushEvent` that can fire on any page (hashtag/mention suggest, markdown preview) must be handled in a shared `attach_hook` in `AuthHooks` (`AutocompleteSuggestHook`, `MarkdownPreviewHook`), never per LiveView. v1.19.1 revived the autocomplete hook (it had thrown on mount since v1.14.1 and broke later LiveView patches, e.g. the timeline pager), which exposed pages without handlers: typing `@` crashed `/profile` and `/admin/settings`. `js_hooks_registered_test.exs` checks every `phx-hook` name is registered (the DM page's `ScrollBottom` never was).
- **Layout is checked geometrically in the browser.** After changing CSS, themes, cards, dropdown menus or how user/remote text is rendered, run `mix test --include feature test/baudrate_web/features/layout_test.exs`. In both Aqua themes, at Firefox's minimum width (500 px window, below Tailwind's `sm`) and at desktop width, it fails when a page scrolls sideways (naming the element, including text overflowing its box) or when a dropdown item is not the topmost element at its centre (clipped by a card, covered by the mobile dock). It found article titles and a profile header that widened the page, and menus whose last items sat under the dock. Fonts differ between machines, so a page can pass locally and fail in the CI image. When scripting such checks, never `scrollIntoView` the element under test: it also scrolls an `overflow: hidden` ancestor and reveals exactly what is clipped.
- **Stale digest artifacts poison browser-based checks.** `Plug.Static` serves a sibling `app.css.gz` / `app.js.gz` (and `mix phx.digest` leaves `app-<digest>.*` + `cache_manifest.json`) in preference to the freshly built `app.css` / `app.js`. They are gitignored, so `git status` stays clean while Wallaby/Firefox quietly loads months-old CSS/JS. Before trusting a screenshot or feature-test rendering, make sure `priv/static/assets/{css,js}/` hold only `app.css` / `app.js` and `priv/static/cache_manifest.json` is absent.
- **Test stability is a priority** — tests must pass deterministically across all partitions under concurrent execution, not just in isolation. Never rely on `Process.sleep` for timestamp separation; use explicit timestamps via `Repo.update_all` instead. Queries with user-visible ordering must include a tiebreaker (e.g. `desc: id`) to avoid nondeterminism when timestamps collide.
